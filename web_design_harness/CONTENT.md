# RSI Harness 汇报文案规划

本次按 `.kimi-code/skills/narrative-tech-writing/SKILL.md` 组织叙事。项目背景与协作流程以用户最新描述为准。

一个章节对应页面上的一个 Tab，章内内容在同一个 Tab 中展开。当前先重构第一章；后续章节重新规划。本文是汇报大纲，流程描述不代表所有能力均已实现。

## 主线

设计师导入一个 React 种子项目 → Agent 泛化到不同场景 → 设计师调试 Skill 并评审产物 → Harness 根据反馈提炼可复用的设计经验 → 更新 Skill → 再生成、再评审，持续迭代。

汇报先交代项目如何运作，让听众理解设计师、Agent 和 Skill 在循环中的关系，再展开支撑这一过程的具体机制。现阶段评测能力可以不齐备，以设计师的判断为准。

## 第一章：从一个种子项目，到可复用的设计经验

**Tab 名称：项目背景**

本章回答：我们的项目在做什么？设计师如何与 Agent 协作？一次评审又如何帮助下一次生成？

### 1. 从设计师手里的一个 Demo 讲起

设计师已经有了一个 React 演示项目（Demo），其中包含具体的页面、样式和交互。我们把它作为“种子”：从这个起点出发，让 Agent 将设计做法泛化到不同场景，并在这个过程中调试技能（Skill）——一份指导 Agent 如何完成设计任务的操作手册。

我们的项目就是与设计师协同工作的 Agent Harness，可以把它理解为一张工作台：设计师在这里导入项目、调试 Skill、评审结果，Agent 则完成生成，并把反馈带回下一轮改进。

### 2. 设计师与 Agent 如何走完一轮协作？

按四个环节介绍日常工作流程：

1. **导入种子**：设计师导入一个 React 项目，为后续生成提供具体的设计起点。
2. **泛化**：Agent 基于种子项目和 Skill，面向不同场景生成新的页面或项目。这里的泛化，是让设计做法适应新的需求。
3. **调试**：设计师结合生成结果检查 Skill 的指导是否有效，调整其中的规则与表达，并重新生成来观察变化。
4. **评审**：设计师查看生成产物、体验交互，指出哪些设计值得保留，哪些存在问题，以及判断的理由。

### 3. 一条标注，怎样沉淀为可执行的设计规则？

设计师在本地评审页面（Local Review）上直接点击产物元素，写下标注意见。系统将元素快照、截图和文字意见保存为原始标注 JSON；一轮评审结束后，标注按轮次归档到需求仓库。Agent 随后逐条对应证据、归并共同根因，并判断问题属于具体场景（Scenario）、可复用的设计配置（Profile），还是负责将设计转成生成规则的转换器，形成一份反馈轮次记录。其中具备跨场景价值的根因，会被提炼为独立的设计规则候选卡，经过“观察 → 评估 → 采纳或废弃”。被采纳的规则再落成机器可执行的检查，接入转换器静态审计、渲染门禁或代码规则检查（lint），并配上能复现问题的失败样例（failure fixture）。这样，后续适用场景在构建和发布时，就能自动检查同一类问题。

这条链路要解决的是：设计师已经指出过的问题，怎样避免每次都靠人重新发现？经验既进入 Skill 的改进过程，也沉淀为持续执行的检查，让一次人工反馈能够约束后续生成。

以“小屏出现孤立分割线”为例，展示从原始标注到机器检查的五个阶段及其产物。

![一条标注留下哪些产物：原始标注、按轮归档、根因归并、规则候选与机器检查](public/rsi/feedback-artifacts-v1.png)

图注：用户提供的 Demo 摘要。分割线规则仍处于观察阶段；第五阶段展示规则被采纳后的目标产物，不代表该规则已经生效。

规则候选按 `observe → evaluate → adopted / deprecated` 流转，也就是先观察、再评估，最终采纳或废弃。用户提供的机器执行 JSON 是另一个候选示例：`candidate-a0b928fab623` 使用 `content-unbound` 失败样例，当前仍是 `evaluate / verifying`。其中的 `user_decision: approved` 表示已有用户批准记录，不能据此将它表述为已采纳、已生效，也不应将它当作分割线规则的执行证据。

### 4. 用一张流程图串起生成、评审与经验沉淀

配图已生成，采用 `DESIGN.md` 的研究刊物风格：暖白纸面、墨色标题、朱红章节号、蓝色循环箭头与少量黄色批注。

![从一次标注到持续检查：生成与评审、根因归并、规则采纳与自动检查](public/rsi/annotation-to-rules-v1.png)

图注：协作流程示意。配图突出跨场景规则沉淀的主链路；反馈也会用于修正对应场景、Profile 或转换器，并带回下一轮生成。候选规则经评估采纳后，在适用范围内生效。

本章落点：**一次人工反馈，沉淀为持续执行的机器检查。** 设计师提供判断，Agent 整理证据并提炼规则；经过评估与采纳后，机器在规则适用范围内反复检查，让设计师把注意力放到新的设计问题上。



# 当前 DDB 工作流缺失的地方



## 轨迹数据全在端侧



设计师在云侧标注，但是在端侧修改，所有的修改轨迹全在端侧，无法采集，全部浪费



![云侧保存了设计意见，但端侧产生的修改轨迹没有被采集](public/rsi/edge-trace-gap-v1.png)

图注：当前工作流缺口。设计师在云侧标注意见，修改和调试却发生在端侧；如果操作步骤、代码修改、页面快照和 Git 提交没有被统一采集，就只剩最终结果，过程证据随之浪费。

## 缺少评测体系

没有统一收集轨迹就很难构建评测体系，全部操作人拉肩扛



![轨迹散落在不同环境中，评测集只能依靠人工整理和反复确认](public/rsi/evaluation-gap-v1.png)

图注：缺少评测体系的现状。没有统一轨迹池时，整理轨迹、配对截图、核对标准和判断结果都依赖人工，形成的评测集也难以稳定复用和持续更新。

# 流程与功能设计

前面讲了设计师和 Agent 如何走完一轮协作。那么，要让这个循环真正跑起来，系统需要哪些功能支撑？

一次循环（loop）其实只有三个动作：**生成 → 反馈 → 更新**，然后回到新的生成。围绕这三个动作，我们把系统拆成六个功能模块：场景用例管理、执行环境管理、标注系统、Skill 版本管理、轨迹和快照管理、评测体系。

## 场景用例管理

场景用例管理本质上就是一个 benchmark（基准测试集）——一份"考题清单"。光有题目（query）还不够：每道题要带上对应的附件，更重要的是要有明确的验收标准，否则生成的好坏无从评判。

![场景用例由任务问题、输入附件和验收标准组成，并进入版本化用例集](public/rsi/case-management-v1.png)

图注：场景用例管理示意。只有同时固定输入与验收标准，不同运行之间的比较才有意义。

## 执行环境管理

系统要能对接不同的执行平台，任务跑完后把轨迹（trace）和产物统一收集回来。产物统一收敛到一个 `dist` 文件夹，后续评审和评测都以它为准。

![不同执行平台通过 CLI 与插件统一收集轨迹，并整理为 dist 产物](public/rsi/runtime-management-v1.png)

图注：执行环境管理示意。平台可以不同，但轨迹证据和最终 `dist` 交付结构需要统一。

## 标注系统

把页面元素可视化地呈现出来，设计师直接在元素上标注，意见和元素一一对应，不再靠口头描述"那个按钮"。

![设计师点击页面元素并留下元素快照、页面截图与文字意见](public/rsi/annotation-system-v1.png)

图注：标注系统示意。意见不仅是一句话，还要能够回到具体元素和问题发生时的页面现场。

![标注系统的元素选取、批注输入和证据附件组件设计](public/rsi/annotation-product-components-v1.png)

图注：标注系统产品组件拆解。设计师先选中具体元素，再填写意见；元素快照、页面截图与文字意见作为一组证据保存。

## Skill 版本管理

Skill 要像 git 一样管理：支持分叉（fork）、合并（merge）、回退（rollback）。每一次改动都有版本可查，改坏了能随时退回去。

![Skill 版本从稳定版分叉为实验版本，比较差异后合并或回退](public/rsi/skill-versioning-v1.png)

图注：Skill 版本管理示意。修改可以分叉、比较、合并和回退，实验版本在验证前不进入稳定主线。

![Skill 版本节点、分叉、差异比较、合并和回退组件设计](public/rsi/skill-product-components-v1.png)

图注：Skill 版本管理产品组件拆解。实验从稳定版本分叉，先比较差异，再选择合并到主线或回退。

## 轨迹和快照管理

每条执行轨迹都在一个独立的 mock workspace 中运行，并由一个 git 仓库全程追踪。执行结束后，把 `.git` 目录静默上传到云端——完整的变更历史随之上云，随时可以复盘。

![每次运行在独立工作区执行，由 Git 时间线记录快照并归档历史](public/rsi/trace-snapshot-v1.png)

图注：轨迹与快照管理示意。`dist` 产物用于复用结果，`.git` 历史用于还原和比较执行过程。

![Git 主线与分叉上的每个轨迹点都对应一个页面效果快照](public/rsi/trace-product-components-v2.png)

图注：轨迹与快照产品组件拆解。Git 管理主线与实验分叉；轨迹上的每个提交点都对应一个页面效果快照，设计师可以沿着分支逐点查看页面如何变化。

## 评测体系

评测体系本身也要不断进化：它要持续识别轨迹和快照，看出快照之间的差异，并按快照的进展打分，把高分和低分正确区分开。

整体上这是两个 Agent 的对弈——负责评测的和负责生成的都要不停迭代，有点像 Agent 版的 GAN（生成对抗网络）：一个出题改卷，一个答题应考，互相逼着对方进步。

![生成 Agent 与评测 Agent 围绕轨迹、差异和样本持续相互校准](public/rsi/evaluation-loop-v1.png)

图注：双 Agent 评测的目标机制。生成与评测共同迭代，高低分样本分别反馈到下一轮生成与评测集更新；该图不代表相关能力已经完整实现。

![大量轨迹数据汇入轨迹池，并按用途组成多个标明轨迹数量的评测集](public/rsi/evaluation-product-components-v2.png)

图注：评测体系的目标组件拆解。大量运行轨迹先汇入轨迹池，再按评测目的组成不同评测集；每个评测集明确显示所包含的轨迹数量，同一条轨迹也可以进入多个集合。图中数量仅作产品设计示意，不代表真实数据。

# 架构设计

架构上采用端云结合的方式。云端负责存储核心资产：Skill 版本、用例、轨迹、快照、评测集等，并按项目区分，配套用户鉴权。

系统有四个主要模块：

- **云端 server**：资产存储与鉴权；
- **客户端 CLI**：数据管理的统一入口；
- **插件系统**：内嵌到不同的 harness 里，通过调用 CLI 管理数据；
- **本地 harness**：实际执行生成任务的环境。

![本地 Harness 通过插件与 CLI 连接云端资产和项目边界](public/rsi/edge-cloud-architecture-v1.png)

图注：端云结合架构示意。本地侧负责执行，云端侧负责鉴权、项目隔离以及重要资产的归档与协作。

# 角色分工

整个流程分三个阶段，每个阶段的主导角色不同：

1. **Demo 生产**：纯粹的设计环境，由设计师主导；
2. **场景泛化 &amp; Skill 打磨**：开发与设计师共创；
3. **数据挖掘**：由算法主导。

![设计、开发与算法在三个阶段轮流主导并持续提供反馈](public/rsi/role-handoff-v1.png)

图注：角色分工示意。主导权随阶段变化，但设计、开发和算法并非彼此割裂，三方始终通过证据与反馈参与同一个循环。
