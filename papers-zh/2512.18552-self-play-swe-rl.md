# 通过自我对弈 SWE-RL 迈向训练超级智能软件智能体（Toward Training Superintelligent Software Agents through Self-Play SWE-RL）
- 作者 / 机构：Yuxiang Wei（魏宇翔）、Zhiqing Sun（孙志卿）、Emily McMilin、Jonas Gehring、David Zhang、Gabriel Synnaeve、Daniel Fried、Lingming Zhang（张令明）、Sida Wang；机构在 arXiv 摘要页未单独列出，作者来自 Meta FAIR（Meta 基础人工智能研究院）与 UIUC（伊利诺伊大学厄巴纳-香槟分校）/ CMU（卡内基梅隆大学）等学术界合作
- 出处：arXiv:2512.18552（已接收为 ICML 2026 主会场论文；v1 提交于 2025-12-21，v3 为 2026-06-02）
- 原文链接：https://arxiv.org/abs/2512.18552

## 摘要（中文翻译）

虽然由大语言模型（large language models, LLMs）与智能体式强化学习（agentic reinforcement learning, RL）驱动的新一代软件智能体能够提升程序员的生产力，但其训练数据（如 GitHub 问题与拉取请求）和环境（如 pass-to-pass 与 fail-to-pass 测试）都严重依赖人类知识或人工整理，这构成了通向超级智能（superintelligence）的根本性障碍。在本文中，我们提出自我对弈 SWE-RL（Self-play SWE-RL, SSR），这是迈向超级智能软件智能体训练范式（training paradigm）的第一步。我们的方法仅需极小的数据假设：只需访问包含源代码与已安装依赖的沙箱化仓库（sandboxed repository），无需人工标注的问题或测试。以这些真实世界代码库（real-world codebase）为基础，我们通过自我对弈（self-play）环境下的强化学习训练一个单一的 LLM 智能体，使其迭代地注入并修复复杂度不断提升的软件缺陷；每个缺陷都由一个测试补丁（test patch）而非自然语言问题描述来形式化界定。在 SWE-bench Verified 与 SWE-Bench Pro 基准上，SSR 取得了显著的自我提升（分别 +10.4 与 +7.8 分），并且在整个训练轨迹中始终优于人工数据基线（human-data baseline），尽管其评估对象是自我对弈中从未出现过的自然语言问题。我们的结果虽然尚属早期，但指明了一条路径：智能体可以自主地从真实世界软件仓库中积累广泛的学习经验，最终使超级智能系统在理解系统如何构建、解决全新挑战以及从零自主创造新软件等方面超越人类能力。

## 核心贡献
- **最小数据假设（minimal data assumptions）**：SSR 只需访问含源代码与依赖的沙箱化仓库（Docker 镜像），无需人工标注的 issue、测试或测试命令。
- **自我对弈训练**：单一 LLM 策略（policy）实例化两个角色——bug 注入智能体（bug-injection agent）与 bug 求解智能体（bug-solving agent），通过 RL 联合训练，双角色共享同一策略参数。
- **以测试工件形式化界定 bug（bug artifact）**：用包含五个可执行文件的"bug artifact"取代自然语言问题描述，为每个 bug 提供完整的可执行规范。
- **高阶 bug 与演化课程（curriculum）**：将求解器失败的修复尝试回收为"高阶 bug"（higher-order bugs，最高到二阶），使任务分布随当前策略持续演化，而非静态数据集。
- **实证结果**：在 SWE-bench Verified 上 +10.4、SWE-Bench Pro 上 +7.8，在整个训练轨迹上持续优于"人工 issue + 测试"的 RL 基线，且改进可泛化到训练中未见的自然语言问题。

## 方法（中文翻译）

**双角色、单策略的自我对弈（dual-role, single-policy self-play）：** "同一个 LLM 策略被划分为两个角色：一个 bug 注入智能体与一个 bug 求解智能体。两个角色都访问同一个容器化环境与同一套工具（如 Bash 和编辑器）。"工具脚手架（scaffold）遵循 CWM（Code World Model）方案；"同一个底层策略 LLM 在两条信号上被联合更新"。

**输入假设（input assumptions）：** SSR 假定"可访问一组含源代码仓库、依赖已安装的 Docker 镜像语料库"，但**不**假定可访问"测试解析器、既有测试、执行测试套件的命令，或任何关于编程语言与测试框架的既有知识"——bug 注入智能体完全通过环境交互自行发现这些信息。

**Bug 工件五件套（bug artifact）：** 一个 bug 被形式化为包含以下五个文件的工件：
1. `test_script.sh` —— 运行测试套件以检测 bug 并验证修复的 Bash 脚本；
2. `test_files.txt` —— oracle 测试文件清单，这些文件在运行测试套件前总会重置为原始版本。这保证了"评估完整性：即使智能体修改或'耍小聪明'地改动测试文件而非真正修复 bug，原始测试也会在评估时被还原"；
3. `test_parser.py` —— 解析测试输出、生成每个测试 ID 与其结果（通过/失败）的详细 JSON 映射的 Python 脚本；
4. `bug_inject.diff` —— 向既有代码库引入 bug 的 git diff 补丁；
5. `test_weaken.diff` —— 删除或削弱既有测试以把 bug 隐藏于测试套件之外的 git diff 补丁。逆转该补丁即定义了"修复必须满足的预期行为，为求解器充当规范"（无需任何自然语言描述）。

**bug 注入策略：** 两种策略用于制造复杂 bug：
- **删除（removal）**：从代码库中删除代码文件或 hunks（补丁块），迫使求解器"重建缺失的功能"；
- **历史回退（history reversion）**：借助 git 日志选择性回退历史代码变更，产生近似真实开发的 bug。
两者都要求"兼容性修复（compatibility fixes）以确保项目保持可运行，从而使任何 bug 都反映真实的语义错误，而非琐碎的语法问题"。

**一致性校验（consistency validation）：** 每个 bug 工件必须通过一系列自动检查，包括：测试文件必须存在且是削弱补丁所涉文件的超集；测试解析器有效；测试脚本有效（通过测试数超过 `min_passing_tests`）；bug 作用范围（`min_changed_files`）；bug 有效性（注入后至少 `min_failing_tests` 个测试失败）；测试削弱有效性；以及**逆变异测试（inverse mutation testing）**——"该检查通过逐个回退 bug 注入补丁中的每个文件，验证补丁中的每个文件都是触发该 bug 所必需的"；若某个文件被回退后原本失败的测试恢复通过，则判定该文件"对 bug 有贡献"，否则拒绝整个工件。这使得奖励信号完全可执行、零人工标注。

**高阶 bug 回收与课程（higher-order bugs / curriculum）：** "我们收集求解智能体失败的初次求解尝试，并利用这些尝试所派生的新 buggy 状态构建新的 bug 工件。"具体而言：原始仓库的 `bug_inject.diff` + `test_weaken.diff` 产生一个 buggy 状态，再叠加求解器失败的 `pred_patch.diff` 形成新的 buggy 状态（并删除/重建 `.git` 目录以防信息泄漏）。这模拟了真实世界中"修好 bug A 又引入 bug B"的情形，并迫使进行多步编辑。论文指出"我们不超过二阶，以防止与既有 bug 重叠的可能性升高"。由于策略在线更新，训练分布"随当前策略持续演化"——这与静态合成流水线（如 SWE-smith、BugPilot）不同。

**奖励设计（reward design）：** 记 s 为求解率（solve rate）、α = 0.8。
- **注入奖励**：一致性校验失败时 −1.0；s = 0 或 s = 1（难度退化）时 −α；0 < s < 1 时取 1 − (1+α)s。"该奖励激励智能体创建既非琐碎可解（s=1）、也非不可解（s=0）的一致性 bug。"
- **求解奖励**：二值奖励，全部测试通过为 +1，否则 −1。

## 实验结果

**实验设置：** 基座模型为 CWM-sft，一个 32B 代码 LLM 检查点（"在其联合 RL 阶段之前"获得）。训练使用 512 张 H100（64 训练 + 448 rollout），150 个全局步（约 2.5B tokens），全局批大小 16M tokens，组大小（group size）8，学习率 3×10⁻⁶。评估采用 SWE-bench Verified（500 个人工验证问题）与 SWE-Bench Pro（731 个公开任务），每问题一次尝试（pass@1），温度 1.0、top-p 0.95。

**关键结果：**
- **自我提升**：SSR 在 SWE-bench Verified 上 **+10.4 分**、在 SWE-Bench Pro 上 **+7.8 分**，且"在两条基准的整个训练轨迹上持续优于基线 RL"——该基线使用相同的环境镜像，但接收人工撰写的 issue 描述与测试套件。即便训练中从未见过自然语言 issue，改进仍能泛化到自然语言 bug 描述。
- **自我对弈组件消融**：full self-play（注入+求解联合训练）显著优于 repair-only（仅修复）与 injection-only（仅注入）。"仅修复训练同样较劣，因为它缺少自我对弈所产生的演化任务分布。"
- **注入方法消融**：直接注入（direct-injection）最差（"倾向产生只有浅层单行修改的琐碎 bug"）；仅删除更强；"删除 + 历史"组合达到最佳性能。
- **奖励消融**：将求解器反馈纳入注入奖励相比仅一致性奖励"只带来轻微、基本可忽略的优势"。
- **评估噪声**：论文承认"评估噪声通常约为 SWE-bench Verified 上 2% 的配对标准误（paired standard error）"。

## 结论与局限

**结论：** SSR 是"通过自我对弈训练超级智能软件智能体"的"第一步"。结果"指明了一条路径：智能体自主从真实世界软件仓库中积累广泛学习经验，最终实现超越人类能力的超级智能系统"——包括理解系统如何构建、解决全新挑战、从零自主创造新软件。工作有望"降低数据采集成本、提升软件工程任务训练的可扩展性，尤其是在标注数据稀缺或过时的场景"。

**局限与风险：**
- **挑战者策略主导（dominant challenger strategies）**：足够聪明的注入智能体可能利用动作空间（例如混淆代码使求解器找不到 bug），或对单一难度参数"隧道视野"（tunnel-vision）式收敛，从而阻断求解器的学习。论文指出，"与二人零和博弈不同，我们并不期望自我对弈去充分探索和利用博弈规则的全部含义"。
- **自然语言关切**："没有人类语言接地（grounding）或人类交互的深层自我对弈，至少在以与当前人类良好沟通为目标时，是前景黯淡的。"缓解手段包括以多样化的真实世界数据为挑战者提供接地，并防止其偏离基于指令（instruction-based）的策略。
- **安全风险**："故意生成 bug 与削弱测试的能力也带来风险，例如被滥用以制造脆弱或误导性的代码工件。因此需要谨慎的沙箱化、负责任的部署并遵守伦理准则。"

## 与 harness × 模型训练的关系

SSR 的意义在于展示了一条去人工标注（annotation-free）的 agent 训练路线：把"找 bug / 修 bug"变成智能体与代码环境之间的自我对弈游戏，训练信号（注入奖励 + 二值求解奖励）全部由可执行测试工件与环境交互自动生成，数据随策略演化自我扩展，从而摆脱对 GitHub issue / PR 等人工整理数据的高度依赖。这对 harness × 模型训练配合的核心启示是：harness 的真正价值是把真实世界代码仓库转化为"可交互、可验证、可自动产出奖励信号"的训练场——沙箱化环境、可执行测试工件、git diff 回滚与一致性校验机制（如逆变异测试）本质上都是 harness 能力，它们让 RL 训练能够在不依赖人工监督的前提下持续发生；而模型训练侧则应通过在线自我对弈让任务难度与分布随策略自适应演化。二者结合，构成了"harness 提供可扩展的交互验证环境，RL 在其中塑造智能体自主注入、定位与修复缺陷的决策能力"的正向循环，为摆脱人工标注瓶颈、迈向更自主的软件智能体铺平道路。
