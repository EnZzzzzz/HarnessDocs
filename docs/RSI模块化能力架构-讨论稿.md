# RSI 模块化能力架构（讨论稿）

> 状态：v0.1，供讨论和继续打磨。本文描述目标能力与技术候选，不代表它们已经实现，也不把候选产品视为最终选型。

## 一、为什么要把 RSI 做成一组独立能力？

设想设计师让一个 Harness 生成页面，指出“窄屏下这条分割线很突兀”。工程师随后修改了 Skill，重新运行，页面看起来好了一些。过了两周，大家想回答一个简单的问题：到底是哪条修改起了作用？

只保存最终页面，回答不了。设计师的意见可能留在云端，代码和操作轨迹留在本地；下一次运行还可能换了任务、模型或执行环境。即使新页面更好，也无法确定是 Skill 改对了，还是比较条件已经变了。

因此，现阶段要建设的递归自我改进流程（RSI，Recursive Self-Improvement），应当是一套可供不同 Harness 接入的公共能力：接住运行过程，让专家判断找到对应的产物，再把可复用的经验变成经过验证的 Skill 改动。Codex、OpenCode、部门的 Octo Agent 和 UCD Studio 可以有不同的执行方式，但交给 RSI 的记录要能放到同一套契约里。

## 二、一份可以复用的数据，究竟由什么组成？

我们关心的核心关系是 **产物、标注、Skill 快照**。但要解释一次结果为什么出现，还得知道任务和执行条件。可以把一次运行看作一张带编号的档案袋：

| 这张档案袋里的部分 | 至少要留下什么 | 回答的问题 |
| --- | --- | --- |
| 起点 | 项目与用例版本、种子项目、Skill/Prompt/Harness 版本、模型与环境配置 | 这次是用什么条件做的？ |
| 过程 | 运行事件、代码改动或 Git 轨迹、失败阶段 | 中途做了什么？ |
| 结果 | 源码或构建产物、截图、日志、产物清单及内容摘要 | 最终生成了什么？ |
| 判断 | 设计师与工程师的标注、所用标准、评审结论与证据位置 | 人为什么认为它好或不好？ |

这里要分清两个时间点。运行结束时，先冻结不可变的**运行快照**（Run snapshot），即使执行失败、尚未有人评审，也保存已经产生的记录和证据。人后来补上的标注是新记录，引用当时的运行 ID、产物摘要和具体页面位置；它不反过来改写原快照。两者关联并校验后，才形成可用于经验提炼和评测的**已标注样本**。这比要求“没有标注就不能归档”更符合真实工作流。

同样，蓝色的“美学目标分布”不是一开始就有的现成答案。它随着设计师在不同任务、品牌和场景下留下判断，才逐渐变得可观察。标注必须带着这些条件保存；否则把风格各异的页面混在一起，只会得到一个含糊的平均值。

## 三、这些能力怎样接成一圈？

**统一接入与运行**负责把不同 Harness 接进来。接入层约定任务开始、关键事件、任务结束和产物登记等接口，并给每次运行分配 Run ID。适配器可以不同，接收端的记录格式要一致。执行端需要独立工作目录、环境与配置快照，并处理超时、失败和取消。

**标注评审**负责让专家把判断留在证据上。设计师提供审美、品牌与体验判断；工程师提供交互可用性、代码质量及工程约束。意见最好能定位到截图、页面元素和对应代码快照，同时记录评审人、标准版本和理由。两类判断可以并列，发生冲突时由人决定取舍，不急着压成一个总分。

**运行采集**负责把端侧容易散落的材料带回来。Harness 插件收集事件、Git 改动、源码、日志、截图与最终产物；本地 CLI 统一处理项目归属、鉴权和同步。网络断开时先进入持久化队列，恢复后补传。采集和上传由确定性的程序承担，不依赖生成 Agent 自觉把文件交齐。

**快照与数据治理**负责给这些材料建立关联。系统为任务、运行、产物、标注和 Skill 版本建立可查询的血缘关系，校验引用是否存在、产物摘要是否一致、标注能否指回受评页面。归档后的快照不可原地覆盖；后补证据、重评和修正都新增记录。数据还要按项目隔离，明确“仅本地、待上传、已上传”等状态。

**经验提炼**从多份已标注样本里找重复出现的原因。例如，设计师在不同页面都指出“小屏出现孤立分割线”，Agent 可以把这些证据聚合成一张规则候选卡，写明适用范围、反例和可能的修复方法。候选先被观察、验证，再由有权限的人采纳或废弃；单次批注不能直接变成全局 Skill。

**Skill 版本管理**保存每一次候选改动的完整内容、父版本、差异和修改理由。实验版本可以从稳定版本派生，在固定任务上验证；通过后再晋升，退步时能回退。Skill 的文件内容和开发轨迹可以使用 Git 管理；产品页面上的版本树、默认版本指针和审批状态仍由平台独立记录，不必硬等同于 Git 分支。

**对照评测与迭代**负责回答“是不是更接近目标”。同一组用例应固定输入和评分规则，比较前后版本时还要核对模型、Harness、环境等条件。评审同时看审美、功能和稳定性，也要看哪些任务退步了。只有在跨场景验证后，才决定保留、继续修改或回退 Skill。

**评测 Agent 学习**放在标注积累后的阶段。它从设计师和工程师的历史判断中学习，先协助处理重复、明确的评审，再把不确定或有争议的案例交还专家。是否真的学会，应在未参与学习的样本上检验；不能把训练样本上的一致率当作自动闭环已经成立。

把这一圈缩成一句话，就是：**统一接入 → 运行与采集 → 冻结快照 → 专家标注 → 整理样本 → 提炼改动 → 对照评测 → 采纳或再迭代**。评测 Agent 是后期加入的加速器，专家判断始终是标准的来源。

## 四、底层技术各放在哪一层？

先按数据的性质分工，避免让一个存储系统包办所有事。

- **Git**：适合保存 Skill、Prompt 等文本内容及需要追溯的代码改动。提交和内容摘要帮助回到当时的文件状态；平台另存业务版本关系、评测关联和发布审批。[Git 数据模型](https://git-scm.com/docs/gitdatamodel)提供了内容对象与引用的基础语义。现有[资产规格](../web_design_harness/public/reference/spec/01-assets.md)也明确：产品版本树不强制采用 Git 作为底层存储。
- **OBS 对象存储**：保存截图、构建产物、快照包和较大的日志。端侧上传可通过限时授权直达对象存储，业务服务只接收元数据与上传回执。[OBS 对象说明](https://support.huaweicloud.com/intl/en-us/usermanual-obs/obs_41_0015.html)与[临时上传授权](https://support.huaweicloud.com/intl/en-us/usermanual-obs/obs_03_1007.html)是可参考的实现机制。这里的 OBS 是候选，不要求架构绑定单一云厂商。
- **关系数据库**：保存项目、用户、Run、版本引用、标注索引、血缘、上传状态和审批记录。早期可以用 PostgreSQL 一类关系库承载这些运营数据；文件本身仍在 Git 或对象存储中。
- **分析数据层**：当样本量和跨轮次分析需求上来，再考虑把结构化轨迹与标注整理为对象存储上的列式数据，并用 Iceberg 一类表格式管理分析快照。[Iceberg 规范](https://iceberg.apache.org/spec/)可作为后续调研起点。OBS 是文件底座，不能单独替代数仓查询、表元数据和数据质量治理。
- **身份与权限**：企业登录、CLI 授权、项目隔离、角色权限和审计贯穿全部模块。若接企业单点登录，可评估 OpenID Connect（OIDC，一套让应用确认用户身份的通用协议）；是否允许采纳规则、发布 Skill，由业务权限决定。[OIDC 规范](https://openid.net/specs/openid-connect-core-1_0-18.html)。这层不应塞进 Git 版本管理模块。

服务形态可以先按模块化单体设计：统一 API 和数据契约，代码按接入、资产、运行、评测、血缘等领域分开。模块边界先立住，部署是否拆成多个服务留待负载和团队协作方式明确后决定。

## 五、先做哪一段，才能验证架构？

第一阶段只挑一个 Harness 跑通最短链路：固定一条用例和一版 Skill，执行、采集、冻结快照，设计师能在产物上留下可回溯的意见。重点验证“同一条意见能找到哪次运行、哪份产物、哪版 Skill”。

第二阶段加入 Skill 派生、固定用例集和前后版本的对照评测。让工程师的判断与设计师的判断都能进入评审，再检查一次改动有没有在别的任务上造成退步。

第三阶段才建设经验候选的半自动提炼，以及学习专家判断的评测 Agent。先让人审候选、审结论；数据量、标注一致性和独立验证效果都足够时，再逐步扩大自动评估的范围。

## 六、下一轮需要讨论什么？

这版还没有把模块边界完全定死。下一轮尤其需要确定四件事：哪些端侧轨迹必须默认采集、哪些只在完整归档时保留；设计师与工程师意见冲突时谁来裁决；Skill 晋升要通过哪些固定任务和退步检查；“OS 登录”具体指操作系统账号、OAuth/OIDC，还是部门已有的单点登录。把这些问题说清，架构图里每条箭头才有准确含义。
