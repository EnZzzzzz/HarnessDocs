# ToolLLM：帮助大语言模型掌握 16000+ 真实世界 API（ToolLLM: Facilitating Large Language Models to Master 16000+ Real-world APIs）
- 作者 / 机构：Yujia Qin, Shihao Liang, Yining Ye, Kunlun Zhu, Lan Yan, Yaxi Lu, Yankai Lin, Xin Cong, Xiangru Tang, Bill Qian, Sihan Zhao, Lauren Hong, Runchu Tian, Ruobing Xie, Jie Zhou, Mark Gerstein, Dahai Li, Zhiyuan Liu, Maosong Sun（共 19 位作者；主要来自清华大学，arXiv 摘要页未列出完整机构信息）
- 出处：arXiv:2307.16789 · ICLR 2024
- 原文链接：https://arxiv.org/abs/2307.16789

## 摘要（中文翻译）

由于当前开源大语言模型（LLM，Large Language Models）的指令微调（instruction tuning）主要集中在基础语言任务上，它们在更高层任务上的能力仍然落后于 ChatGPT 等闭源模型——例如适当地与工具（API）交互以完成复杂的人类指令。为了弥合开源与闭源模型在工具使用（tool-use）能力上的差距，我们提出 ToolLLM，一个涵盖数据构建、模型训练与评估的通用工具使用框架。我们利用 ChatGPT 构建了 ToolBench，一个指令微调数据集。ToolBench 的构建包含三个阶段：（1）API 收集：我们从 RapidAPI Hub 收集了涵盖 49 个类别的 16,464 个真实 RESTful API；（2）指令生成：我们利用 ChatGPT 生成覆盖单工具与多工具场景的多样化指令；（3）解决方案路径标注：我们利用 ChatGPT 搜索有效的解决方案路径（即一系列 API 调用序列），并设计了一种新颖的基于深度优先搜索的决策树（DFSDT，Depth-First Search-based Decision Tree）算法来增强 ChatGPT 的规划与推理能力，使其能够评估多条推理轨迹，并在更广阔的搜索空间中寻找有效答案。我们开发了一个高效的自动评估器 ToolEval，并利用 ToolBench 对 LLaMA 进行微调，得到 ToolLLaMA，同时配备一个神经 API 检索器（neural API retriever），能够自动为给定指令选择合适的 API。实验表明，ToolLLaMA 在执行复杂指令方面表现出与 ChatGPT 相当的性能，能够泛化到未见过的 API，并在分布外（OOD，out-of-distribution）的 APIBench 数据集上展现出强大的零样本（zero-shot）泛化能力。

## 核心贡献

- **ToolBench**：利用 ChatGPT 以三阶段自动流程构建的高质量指令微调数据集。涵盖 3,451 个高质量工具（16,464 个真实 API），生成 126,486 条指令-解决方案路径对（含 469,585 次真实 API 调用），同时支持单工具与多工具场景。相比先前数据集（APIBench、API-Bank、ToolAlpaca 等），首次同时具备"真实 API""多工具场景""API 检索""多步推理"等特性。
- **DFSDT**：一种新颖的基于深度优先搜索的决策树决策策略。它让模型能够评估多条推理轨迹、沿最有希望的路径继续推进、或通过"放弃（Give Up）"放弃某个节点并扩展新节点，从根本上解决了 ReACT 缺乏"决策回溯"机制、错误会级联传播的问题。在同等成本下显著超越 ReACT（平均 pass rate 63.8% vs. ReACT 35.3%、ReACT@N 44.5%）。
- **ToolEval**：自动评估器，采用两个指标——通过率（pass rate，模型能否在有限预算内完成指令）与胜率（win rate，两条解决方案路径的相对质量比较）。与人类标注的一致性分别达到 87.1% 和 80.3%。
- **ToolLLaMA + API 检索器**：微调 LLaMA-2 7B 得到 ToolLLaMA，并配一个基于 Sentence-BERT 的稠密检索器，从 16,000+ API 池中自动推荐相关 API，免去人工指定 API 集合；实验证明使用检索到的 top-5 API 甚至优于使用"标准答案（oracle）"API 集合。
- **关键发现**：ToolLLaMA 超越 Text-Davinci-003 与 Claude-2，几乎与 ChatGPT 持平，略逊于 GPT-4；对未见过的 API 具有良好的泛化能力，并在 OOD 的 APIBench 数据集上达到与 Gorilla 相当的水平。此外，Vicuna 与 Alpaca 在大量提示工程下通过率仍为 0%，表明常规指令微调的能力无法覆盖工具使用领域。

## 方法（中文翻译）

整体框架包含数据构建（ToolBench）、推理策略（DFSDT）、自动评估（ToolEval）与工具选择（API 检索器）四个部分。

### 1. ToolBench 数据集构建

ToolBench 通过 ChatGPT（gpt-3.5-turbo-16k，启用 function calling）以三阶段流程自动构建，仅需极少的人工监督。

**（1）API 收集（API collection）。** RapidAPI 是一个 API 市场，包含 49 个粗粒度类别（如体育、金融、天气等）和 500 多个更细粒度的"集合（collection）"（如中文 API、数据库 API）。每个工具（tool）包含多个 API。作者为每个工具抓取工具名、描述、主机 URL 以及全部 API；为每个 API 抓取名称、描述、HTTP 方法、必选/可选参数、请求体、可执行的代码片段以及一个示例响应。经过过滤：从最初的 10,853 个工具（53,190 个 API）中剔除无法正常调用的 API（返回 404、内部错误）、响应过慢的 API 以及低质量响应（HTML 源码、错误信息）的 API，最终保留 **3,451 个高质量工具（16,464 个 API）**。

**（2）指令生成（instruction generation）。** 不是从零开始头脑风暴指令，而是先采样 API 组合、再围绕它们生成指令。对每个采样到的组合，让 ChatGPT 输出若干指令以及每条指令对应的相关 API 子集（后者用于训练检索器）。提示中包含：（a）任务描述；（b）每个采样 API 的完整文档；（c）3 个上下文内（in-context）种子示例（人工撰写的 12 条单工具 + 36 条多工具种子，随机采样）。采样策略分三种：
- **I1（单工具）**：遍历每个工具，为其 API 生成指令，得到 87,413 条（指令，相关 API）对；
- **I2（类别内多工具）**：从同一 RapidAPI 类别中随机选取 2–5 个工具，得到 84,815 条；
- **I3（集合内多工具）**：从同一 RapidAPI 集合中随机选取 2–5 个工具，得到 25,251 条。

含有幻觉（不存在）相关 API 的指令会被过滤掉，最终约 20 万条（指令，相关 API）对。

**（3）解决方案路径标注（solution path annotation）。** 给定一条指令，让 ChatGPT 在多轮对话中搜索一个有效的动作序列。每个动作格式为 "Thought: …，API Name: …，Parameters: …"。每个 API 以函数（function）形式填入 ChatGPT 的 function-calling 字段，并额外定义两个函数："以最终答案结束（Finish with Final Answer）"（以最终答案作为参数）和"放弃结束（Finish by Giving Up）"（用于给定 API 无法完成指令的情况）。作者指出，CoT/ReACT 在此场景失败的原因有二：（a）错误传播——例如反复错误调用 API 或幻觉出根本不存在的 API；（b）只沿单一方向探索，缺乏广度。DFSDT 因此构建一棵决策树：模型可以沿有希望的路径继续，或通过"放弃结束"放弃当前节点并扩展新节点；扩展节点时以之前生成的节点作为提示，并明确鼓励生成与既有节点不同的方案。作者选择深度优先搜索（DFS，Depth-First Search）而非广度优先搜索（BFS），因为标注在找到第一条有效路径时即结束，BFS 会消耗过量的 OpenAI API 调用。最终仅保留成功通过的解决方案路径：**126,486 条（指令，解决方案路径）对**用于训练 ToolLLaMA。

**DFSDT 的实现细节：** 经典 DFS 需要先对子节点排序，这是最耗费资源的一步（需要 O(n log n) 次评估调用）。作者经验性地发现，最先生成的节点通常排名最高，因此**跳过排序、直接采用前序遍历（pre-order traversal）**。如果模型从不回溯，DFSDT 就退化为 ReACT（二者效率相当）；完成遍历后探索的节点与经典 DFS 几乎一致，因此仍能处理复杂指令。换言之，ReACT 是 DFSDT 的一个退化版本，ToolLLaMA 在推理时既可用 DFSDT 也可用 ReACT。

### 2. ToolEval 自动评估器

- **通过率（pass rate）**：在有限预算内成功完成指令的比例，衡量可执行性。评估器先判断指令可解还是不可解，再在详细规则下将每条路径标注为 **Pass / Fail / Unsure**。例如：穷尽尝试 API 后"放弃结束"记为 Pass；明明有有效 API 信息却拒绝执行记为 Fail；给出幻觉的最终答案记为 Fail；对不可解指令，无论给出有效完成还是拒绝均记为 Pass。
- **胜率（win rate）**：比较同一指令的两条解决方案路径；通过的候选优于失败的候选，否则评估器依据六个标准打分：**信息丰富度（information richness）、事实性（factuality）、推理质量（reasoning）、里程碑（milestone，达到的里程碑数量）、探索度（exploration，尝试更多潜在可用 API 更优）、成本（cost，冗余 API 调用更少更优）**。每条路径至少评估 4 次并多数投票取最终结果。
- **一致性验证**：ToolEval 与人类标注在通过率上一致率为 87.1%、胜率上为 80.3%。论文指出，工具使用的评估比对话评估更难——即使是人类专家也经常意见分歧（例如偏好"用少量 API 快速作答"还是"穷尽交叉验证"）。

### 3. API 检索器

基于 Sentence-BERT（BERT-BASE）的稠密检索器：将指令和每个 API 文档编码为向量，用向量相似度打分相关性。训练时以第 2 阶段产生的相关 API 标注为正样本、采样的其他 API 为负样本（对比学习）。基线为 BM25 与 OpenAI 的 text-embedding-ada-002。用 NDCG@1 与 NDCG@5 在 I1/I2/I3 上评估：

| 方法 | I1 NDCG@1/@5 | I2 NDCG@1/@5 | I3 NDCG@1/@5 | 平均 NDCG@1/@5 |
|---|---|---|---|---|
| BM25 | 18.4 / 19.7 | 12.0 / 11.0 | 25.2 / 20.4 | 18.5 / 17.0 |
| Ada | 57.5 / 58.8 | 36.8 / 30.7 | 54.6 / 46.8 | 49.6 / 45.4 |
| **Ours（本文）** | **84.2 / 89.7** | **68.2 / 77.9** | **81.7 / 87.1** | **78.0 / 84.9** |

检索器一致地优于基线；单工具检索（I1）比多工具检索（I2、I3）更简单。

## 实验结果

### 1. 初步实验：DFSDT vs. ReACT

基于 ChatGPT 的通过率对比（ReACT@N 为成本匹配基线——多次运行 ReACT 直到总成本与 DFSDT 相当）：

| 方法 | I1 | I2 | I3 | 平均 |
|---|---|---|---|---|
| ReACT | 37.8 | 40.6 | 27.6 | 35.3 |
| ReACT@N | 49.4 | 49.4 | 34.6 | 44.5 |
| **DFSDT** | **58.0** | **70.6** | **62.8** | **63.8** |

DFSDT 在所有场景均显著优于两个基线，在更难的 I2、I3 多工具指令上提升最大——说明它能解决 vanilla ReACT 无论重复多少次都无法解决的复杂指令。由于只保留通过的标注作为训练数据，DFSDT 还降低了总标注成本。

### 2. 主实验：ToolLLaMA vs. 闭源模型

**ToolLLaMA**：在指令-解决方案对上微调 LLaMA-2 7B。由于 API 响应可能很长，通过位置插值（positional interpolation）将原始 4,096 token 上下文扩展到 8,192；使用学习率 5×10⁻⁵、warmup 比例 4×10⁻²、batch size 64、最大序列长度 8,192、位置插值比例 2，训练 2 个 epoch。

**泛化设置**（用于测试泛化能力，分为三层）：(1) **Inst.**（未见指令、已见工具）；(2) **Tool**（已见类别中的未见工具）；(3) **Cat.**（未见类别中的未见工具）。I1 测试全部三层，I2 测试 Inst. 与 Cat.，I3 只测 Inst.（集合已跨类别）。测试指令给定标准答案（oracle）API 集合。**基线**：Vicuna、Alpaca、ChatGPT、Text-Davinci-003、GPT-4、Claude-2，各配 ReACT 与 DFSDT。胜率以 **ChatGPT-ReACT** 为参照基准，>50% 即优于 ChatGPT-ReACT。

**表：六个设置的平均通过率 / 胜率（Pass / Win）**

| 模型 | 方法 | 平均 Pass | 平均 Win |
|---|---|---|---|
| ChatGPT | ReACT | 40.2 | – |
| ChatGPT | DFSDT | 64.8 | 64.3 |
| Claude-2 | ReACT | 6.8 | 34.4 |
| Claude-2 | DFSDT | 22.6 | 43.5 |
| Text-Davinci-003 | ReACT | 16.5 | 33.2 |
| Text-Davinci-003 | DFSDT | 43.1 | 46.3 |
| GPT-4 | ReACT | 57.2 | 64.4 |
| GPT-4 | DFSDT | **71.1** | **70.4** |
| Vicuna | ReACT & DFSDT | 0.0 | 0.0 |
| Alpaca | ReACT & DFSDT | 0.0 | 0.0 |
| ToolLLaMA | ReACT | 29.0 | 47.0 |
| ToolLLaMA | DFSDT | 66.7 | 60.0 |
| ToolLLaMA | DFSDT-Retriever | 67.3 | 63.1 |

**主要发现：**
1. 尽管进行了大量提示工程，Vicuna 与 Alpaca 未能通过任何指令（通过率与胜率均为 0.0），说明其指令遵循能力并未覆盖工具使用领域。
2. 对所有 LLM，DFSDT 在通过率与胜率上均显著优于 ReACT；值得注意的是，ChatGPT+DFSDT 的通过率超过了 GPT-4+ReACT。
3. ToolLLaMA+DFSDT 大幅优于 Text-Davinci-003 与 Claude-2，达到"几乎与 ChatGPT 持平"的水平，其平均通过率仅次于 GPT-4+DFSDT——同时还能泛化到未见的指令与工具。

**集成检索器**：将 top-5 检索到的 API（而非标准答案集合）输入模型，通过率与胜率均进一步提升（66.7→67.3、60.0→63.1），因为某些标准答案 API 可以被检索器发现的更相似、功能更好的 API 替代。这验证了在 16,000+ API 池上检索器的有效性。

### 3. OOD 泛化到 APIBench

在三个 APIBench 领域（TorchHub、TensorHub、HuggingFace）上不做任何训练更新直接评估 ToolLLaMA，使用训练好的检索器或 oracle 检索器，与在 APIBench 上微调的 Gorilla（LLaMA-7B）的零样本（ZS）与检索增强（RS）设置对比。指标为 AST 准确率（AST，抽象语法树匹配准确率，越高越好）与幻觉率（越低越好）。

| 方法 | HuggingFace | TorchHub | TensorHub |
|---|---|---|---|
| ToolLLaMA + Our Retriever | 10.60 / **16.77** | 15.70 / **51.16** | 6.48 / 40.59 |
| Gorilla-ZS + BM25 | 46.90 / 10.51 | 17.20 / 44.62 | 20.58 / 34.31 |
| Gorilla-RS + BM25 | **6.42** / 15.71 | **5.91** / 50.00 | **2.77** / **41.90** |
| ToolLLaMA + Oracle | 8.66 / 88.80 | 14.12 / 85.88 | 7.44 / 88.62 |
| Gorilla-ZS + Oracle | 52.88 / 44.36 | 39.25 / 59.14 | 12.99 / 83.21 |
| Gorilla-RS + Oracle | 6.97 / **89.27** | 6.99 / **93.01** | 2.04 / **94.16** |

（每格为"幻觉率 ↓ / AST 准确率 ↑"）

ToolLLaMA + 训练好的检索器在 HuggingFace 与 TorchHub 的 AST 准确率上超过 Gorilla+BM25（ZS 与 RS 两种设置）；在 oracle 检索器下，ToolLLaMA 一致优于 Gorilla-ZS。论文指出，由于 ToolBench 的设置更复杂（多工具使用、多步推理），Gorilla 无法泛化回 ToolBench。在 APIBench 实验中，每个 API 被表示为一个函数，用于选择 API、生成调用代码并用自然语言描述输出；由于 ToolLLaMA 训练时从未见过这些 API，因此不考虑零样本（无 API 描述）设置。

## 结论与局限

**结论。** 论文提出了一套在 LLM 中激发工具使用能力的方法与系统：**ToolBench** 覆盖 16k+ 真实 API，同时包含单工具与多工具场景，通过 ChatGPT 以极少人工监督构建；**DFSDT** 强化了规划与推理能力；**ToolEval** 提供高效可靠的自动评估；**ToolLLaMA** 达到与 ChatGPT 相当的性能并能泛化到未见 API；神经 **API 检索器**让工具使用流程更加自动化，并展现出分布外泛化能力。这项工作"为指令微调与工具使用交叉领域的未来研究铺平了道路"。

**局限。** 论文没有专门的"局限"章节，相关讨论散落在 ToolEval 附录等处：（1）工具使用评估远比对话评估复杂——每条指令可能存在无限条"正确"解决方案路径，即使是人类专家也经常对哪条路径更好意见不一，导致标注一致性相对较低（87.1% / 80.3%），作者坦言"工具使用领域的公平评估仍有很长的路要走"；（2）ToolEval 依赖 ChatGPT 作为裁判，标注与评估均依赖 OpenAI API 成本（DFSDT 消耗更多调用，已通过前序遍历变体缓解）；（3）API 池局限于 RapidAPI 平台；（4）APIBench OOD 评估省略了零样本（无 API 描述）设置。此外可隐含推论：数据构建与评估成本偏高、可扩展性受闭源 API 服务约束等。

## 与 harness × 模型训练的关系

从 agent harness（运行框架）角度看，ToolLLaMA 的推理流程本质上是一个"模型 + 检索器 + 工具执行环境 + 决策循环"的组合：API 检索器负责工具选择的自动化，DFSDT 相当于一个带回溯能力的决策式 agent 循环（替代了 ReACT 式的"推理-行动"循环），ToolEval 则扮演自动评判器（judge）的角色来评估 agent 的轨迹质量——这些模块组合起来即是一个完整的 agent harness 设计，其中 DFSDT 的"评估多条轨迹、可放弃节点"机制与当前基于树的搜索式 agent harness 直接呼应。从模型训练角度看，该论文的核心主张是：仅靠通用指令微调不足以赋予模型工具使用能力（Vicuna/Alpaca 通过率 0%），必须用"真实 API 调用的多轮解决方案轨迹"作为训练语料进行监督微调（SFT），并让检索器参与样本构造来训练工具选择能力；这为"用 agent 轨迹数据训练模型"提供了可复现的数据构建与标注方法论。它同时提示了三个训练层面的可借鉴点：以"放弃/回溯"标注教会模型放弃幻觉 API、用函数调用（function calling）格式统一工具接口、以及通过位置插值扩展上下文以容纳长 API 响应。
