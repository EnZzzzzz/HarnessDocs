# 从问答到任务完成：智能体系统与 Harness 设计综述（From Question Answering to Task Completion: A Survey on Agent System and Harness Design）

## 摘要（中文翻译）

基于大语言模型（LLM）的智能体，标志着从被动的问答（passive question answering）向主动的任务完成（active task completion）的转变：它们感知环境、调用工具、维护状态，并在很长的时域内持续行动。智能体工程的重心已从提示词工程（prompt engineering）演进到工作流（workflows）、上下文工程（context engineering）、harness 工程（harness engineering），再演进到智能体原生的训练（agent-native training）与协同进化（co-evolution）。这引出一个核心问题：智能体性能的瓶颈究竟位于何处——是基础模型、执行 harness（execution harness），还是二者之间的耦合（coupling）？

本综述以"model–harness"（模型–运行时）的视角考察 LLM 智能体：一个智能体可表述为"基础模型 + 执行 harness"的组合。我们梳理了模型中心式（model-centric）扩展的局限性，识别出四个智能体工程范式，并将执行 harness 分解为六个相互耦合的运行时职责（runtime responsibilities）：观察（observation）、上下文（context）、控制（control）、动作（action）、状态（state）与验证/治理（verification/governance）。我们给出智能体的功能性定义，将任务属性与 harness 配置之间的对应关系绘制成图，综合了 model–harness 的证据，回顾了评测基准，并讨论了开放挑战，包括价值感知的评测（value-aware evaluation）、安全性（safety）、harness 泛化（harness generalization）以及模型–harness 协同进化。我们的核心主张是：智能体的质量——包括成功率、效率、安全性与泛化能力——并非仅由模型单方面决定，而是由模型能力、运行时基础设施、任务结构与评测设计四者之间的相互作用共同涌现。

## 核心框架：model–harness 视角

综述区分了智能体的两种定义方式：**功能性定义**关注"一个智能体必须做什么"——感知环境、维护状态、推理、行动、适应，即"智能体是一个目标导向的闭环系统（goal-directed closed-loop system）"；**实现性定义**关注"这些功能如何实现"，即一个智能体是模型与 harness 的配对：

> A_LLM = ⟨M, H⟩ = ⟨M, I_obs, C, L, I_act, S, V⟩

其中 M 是基础模型，负责灵活的语言理解、推理、规划与动作提议；H 是执行 harness，提供运行时机制。作者强调，这一区分弥合了经典智能体定义与近期的 harness 中心式叙述之间的鸿沟，并指出 agent 性能是 **model–harness 配对**的性质，而不是任一组件的孤立属性。

Harness 被形式化为一个运行时设计对象，由 **6 个相互耦合的运行时职责**组成：

1. **观察接口（Observation interface, I_obs）**：把原始环境信号转换为模型可用的观察，包括终端输出、文件差异（diff）、截图、DOM 状态等。
2. **上下文管理器（Context manager, C）**：决定什么信息进入模型上下文、何时进入、以何种形式进入。
3. **控制循环（Control loop, L）**：编排"观察—推理—行动—反馈"循环，包括步骤调度、停止条件、重试、反思（reflection）、委派（delegation）。
4. **动作接口（Action interface, I_act）**：把模型输出映射为可执行操作，如函数调用、MCP 工具、shell 或代码执行。
5. **状态与产物存储（State and artifact store, S）**：持久化执行状态与产物，包括对话历史、计划、草稿区（scratchpad）、检查点、日志、轨迹、diff。
6. **验证与治理层（Verification and governance layer, V）**：通过测试、断言、验证器模型、沙箱策略与权限门（permission gate）来检查、约束并修复执行。

作者强调这六项职责是**相互耦合**的：改动其中一项，负担会向其他项转移。因此，任务并非仅仅是一个应用标签，而是一个"**压力剖面**（pressure profile）"——不同的任务属性把性能瓶颈压向 harness 的不同组件：任务时域主要压向上下文、状态与控制；环境类型主要压向观察、动作与安全边界；自主性主要压向验证、日志与恢复；弱/延迟的 oracle 需要出处（provenance）与审查；不可逆动作需要治理；高自主性需要日志、预算与恢复。按领域看，软件工程把主要瓶颈放在**验证与治理**上，Web 与 GUI 智能体把瓶颈从验证转向**落地/锚定（grounding）**，科学智能体转向**综合（synthesis）**，具身智能体转向**实时控制**，而安全关键场景则转向**安全性**。

## 范式演进（4 个阶段）

作者把智能体工程梳理为四个范式，并强调它们"构成一个概念性的进化视角，而非严格的时间划分——如今实践中四者并存"：

1. **Phase 1 — 提示词工程（Prompt Engineering）**：优化发送给模型的单轮指令。本质上解决的是一个"**表达问题**（expression problem）：如何提问"，而非"信息问题（information problem）"。
2. **Phase 2 — 工作流与上下文工程（Workflows / Context Engineering）**：把优化单元从单条提示词扩展到多步执行周围的信息生命周期；上下文被视为一个动态组装的运行时对象，形式化为 C = A(c1, c2, …, cn)，即由多个信息块装配而成。
3. **Phase 3 — Harness 工程（Harness Engineering）**：**闭环**。harness 引入反馈驱动的执行：模型行动、观察环境响应、并基于观察进行推理。这构成了由外部状态支撑的闭环 agentic 循环。
4. **Phase 4 — 智能体原生训练与协同进化（Agent-Native Training & Co-Evolution）**：规划、工具使用、验证、恢复等智能体行为，越来越多地通过交互式环境被训练进模型参数中；在协同进化下，"模型、harness 与改进循环都可以从执行轨迹中被共同更新"。

## 关键证据

同一模型在跨 harness 时性能可差两位数的证据，来自多个基准与代表性工作：

- **静态基准正在饱和，agentic 基准仍远未解决**：MMLU、GPQA、HumanEval 等在前沿上日益饱和，而 SWE-bench、WebArena、OSWorld、TheAgentCompany、Terminal-Bench 等 agentic 任务仍保留着巨大的上升空间。近期 GPT、Claude、Gemini 系列发布的模型得分区间越来越窄，评测遭遇结构性困难；Humanity's Last Exam 等更难的评测被提出以恢复区分力，而数据污染（contamination）风险进一步使解读复杂化。
- **纯模型扩展收益递减**：以 LLaMA3.1 为例，从 70B 升级到 405B 将训练算力从 7.0M 提升到 30.84M H100 GPU 小时，但在代表性基准上仅换来有限增益——MMLU +2.6 分、MBPP EvalPlus +2.6 分、GSM8K +1.7 分。这暗示：若仅靠模型扩展无法在 agentic 任务上弥合差距，那么起作用的究竟是什么？
- **SWE-agent（ACI 重设计）**：重设计"智能体–计算机接口"（agent–computer interface, ACI）在**固定基础模型**下能大幅提升 SWE-bench 表现——因为重设计同时改变了模型"看到什么"与"如何行动"，是"观察–动作协同设计"的典型样例。
- **Meta-Harness**：更进一步，把 harness 优化本身当作一个**搜索问题**，证明自动改进的 harness 在 Terminal-Bench 上能胜过手工设计的基线。
- **NLAH**：把 harness 逻辑形式化为可编辑、可移植的自然语言产物，通过受控消融实验证明其贡献可度量、可叠加（measurable and additive）。
- 评测维度还覆盖任务时长、步数、环境不确定性、工具使用复杂度、状态持久性与恢复需求；例如以"在固定成功概率下能完成的类人任务时长"来评测智能体。SWE-bench、BigCodeBench、LiveCodeBench 等表明，编程能力依赖仓库级上下文。

## 结论与展望

**结论**：harness 工程已从"实现细节"转变为"**一等设计对象**（first-class design object）"。可靠的长时间域任务完成，越来越要求"一个由多个模型之上的可组合、可优化的运行时"来实现，而不再只依赖提示词技巧。模型能力要转化为与环境的持续、可检查的交互，关键在 harness 的设计。

**开放问题**（综述第 8 节归纳的四个主要挑战，以及各职责对应的未解问题）：

1. **价值感知评测（Value-aware evaluation）**：突破"任务是否成功"的单一标准，纳入效率、成本与安全性；也需处理评测协议与训练/运行接口耦合导致的解读偏差。
2. **安全性（Safety）**：自主系统的治理、沙箱化与安全终止。
3. **Harness 泛化（Harness generalization）**：设计能跨域迁移的运行时策略（控制策略在时域与领域间的鲁棒性）。
4. **模型–harness 协同进化（Model–harness co-evolution）**：在部署过程中联合改进模型与运行时。

此外还有：如何在部分可观测性（partial observability）下设计忠实且对决策有用的观察接口；如何在上下文成本受限时保持摘要保真与状态完整性；如何设计兼具表达力与可治理性的动作抽象；如何在支持回滚、委派与记忆复用的同时维护状态保真；如何设计有选择性且成本敏感的验证机制；如何区分可恢复的局部错误与更深层的任务级崩溃；以及"智能体行为有多少被学进模型、又有多少留在运行时中"这一根本性问题。

## 与 harness × 模型训练的关系

这篇综述是 harness 项目的核心参考，原因有三。其一，它提供了统一的概念词汇——"model–harness 配对决定 agent 能力"这一视角，以及 6 个运行时职责（observation / context / control / action / state / verification–governance）的分解——这正是整个 harness 方向（EZAgent / HiAgent 及后续各线工作）共同使用的分析语言。其二，它用 benchmark 证据（SWE-bench / Terminal-Bench / WebArena 上同一模型跨 harness 性能可差两位数，及 LLaMA3.1 纯扩展收益递减）为"harness 是性能杠杆"提供了核心论据，直接支撑项目把 harness 视为一等优化面而非实现细节的立场。其三，它把 **agent-native training 与协同进化**定位为第四个范式，并把"模型行为有多少被训练进参数、多少留在运行时"列为开放问题——这恰好是"harness × 模型训练"这条研究线的出发点（Polar、OpenForge RL、MemoHarness、SIA、HASE 等均在此问题域内），因此该综述同时是项目的框架底座与 related work 的入口。
