# 极：在任意 harness 上进行大规模 Agentic 强化学习（Polar: Agentic RL on Any Harness at Scale）
- 作者 / 机构：Binfeng Xu, Hao Zhang, Shaokun Zhang, Songyang Han, Mingjie Liu, Jian Hu, Shizhe Diao, Zhenghui Jin, Yunheng Zou, Michael Demoret, Jan Kautz, Yi Dong（arXiv 摘要页未标注机构；投稿人为 Shaokun Zhang）
- 出处：arXiv:2605.24220 [cs.DC]，2026 年 5 月 22 日提交（v1），17 页，6 图，2 表
- 原文链接：https://arxiv.org/abs/2605.24220

## 摘要（中文翻译）

针对语言智能体（language agents）的强化学习（Reinforcement Learning, RL）越来越依赖定制的 harness（即智能体运行框架/执行环境，用于管理长上下文、多轮工具调用与多智能体编排）。然而，把这类 harness 移植到 RL 环境接口中仍然困难，而且往往会丢失重要的训练信号。本文提出 Polar，一个用于在任意 agent harness 之上进行可扩展异步 RL 的 rollout（采样/回放）框架，以弥合这一鸿沟。Polar 把 agent harness 当作黑盒（black box）处理：它代理（proxy）LLM API 调用，记录 token 级（token-level）的模型交互，并重建出对 token 忠实（token-faithful）的轨迹（trajectory）用于训练。每个 rollout 节点以并行的方式高效管理运行时预热（runtime prewarming）、智能体执行、轨迹重建与评估，对外暴露异步服务端点（asynchronous service endpoints），可被独立的训练器（trainer）在规模上消费。这种解耦设计使 Polar 与 agent harness、训练基础设施和 RL 算法均无关（agnostic），同时提高了长时运行智能体工作负载的算力利用率。我们通过在软件工程任务上用主流编码 harness 训练智能体来验证 Polar。使用简单的 GRPO，Polar 在 Codex、Claude Code、Qwen Code 与 Pi 这四种 harness 上，分别把 Qwen3.5-4B 在 SWE-Bench Verified 上的成绩提升了 22.6、4.8、0.6 和 6.2 个百分点。我们进一步展示了 Polar 在自定义 harness 上进行离线数据生成（offline data generation）的能力，并对轨迹重建策略做了消融实验。Polar 重写了其前作 Prorl Agent，并已注册为 NeMo Gym 环境之一。

## 核心贡献

- **基于代理（proxy）的 rollout 与轨迹重建**：以智能体的 LLM API 载荷作为 RL 的 rollout 接口，让现有 harness 无需修改内部代码即可直接充当 RL 环境——回答论文的中心问题「我们能否在不打开黑盒的情况下对智能体做 RL 训练？（Can we train agents with RL without opening the box?）」其关键观察是：任何基于 LLM 的智能体都必须与模型通信，因此模型 API 边界是存在于智能体自身之外的公共接口。
- **Rollout-as-a-service 架构**：任务提交、运行时设置、harness 执行、轨迹重建、评估与训练器回调（trainer callbacks）全部解耦在异步服务边界之后，使 rollout 可独立于训练与推理进行扩展。
- **对 token 忠实的轨迹重建**：把原始模型请求转换为对 token 忠实的轨迹，提供保守的逐请求（per-request）重建与用于重型 rollout 的前缀合并（prefix merging）策略，并通过注册表（registry）提供可扩展接口。
- **端到端验证**：在主流编码 harness 上完成 RL 训练，并用自定义编码 harness 完成离线 SFT 数据生成。

## 方法（中文翻译）

### 总体思路

Polar 的核心设计是把集成边界（integration boundary）移到模型端点（model endpoint）上：harness 正常运行，代理（proxy）旁路观察 token 级流量，rollout 服务把已完成的执行过程转换为可训练的轨迹与奖励。由此，rollout 可以在不破坏 harness 非标准行为的前提下，独立于训练与推理进行扩展。

### 架构：两大核心组件

- **Rollout 服务器（Rollout server）**：接收 TaskRequest（任务请求），将其扩展为 `num_samples` 个相互独立的会话（session），派发给网关节点（gateway node），持久化最终结果，并暴露轮询状态接口。
- **网关节点（Gateway node）**：管理会话生命周期（启动运行时 → 准备 harness → 运行命令 → 构建轨迹 → 评估 → 拆除），并托管模型代理端点。

### 代理捕获（Proxy capture）：每个模型请求的 4 个步骤

1. **检测提供商 API（Detect provider API）**：通过请求路径与请求头区分 Anthropic Messages、OpenAI Chat Completions、OpenAI Responses 与 Google generateContent 风格的调用。
2. **规范化请求（Normalize request）**：用转换器把角色（roles）、内容部件（content parts）、工具定义（tool definitions）、工具选择（tool choices）、停止控制（stop controls）、生成参数统一转换为 OpenAI Chat Completions 形状，并加上 `logprobs=true`。
3. **捕获 token 级数据（Capture token-level data）**：存储请求消息、响应消息、prompt token ID、采样得到的响应 token ID、结束原因（finish reason）以及来自推理后端的对数概率（log probabilities）。
4. **返回提供商形状（Return provider shape）**：对流式（streaming）请求，先获取非流式上游响应，再发出一个合成出的、符合提供商形状的流（synthetic provider-shaped stream），从而在保持 SSE 兼容性的同时实现忠实的捕获。

### Harness 适配器与运行时

适配器（adapter）很轻量：负责安装配置、注册 MCP 服务器/技能（skills）、写入提供商设置、返回 shell 命令。内置 claude_code、codex、gemini_cli、qwen_code、opencode、pi 等快捷方式。运行时实现 start/stop/exec/upload/download/cancellation；首个版本支持用于 HPC 的 Docker 与 rootless Apptainer。

### 异步 rollout 分阶段

每个网关使用相互隔离的工作线程池（worker pools）来分别处理 INIT、RUNNING、POSTRUN 阶段，外加一个有界的 READY 缓冲。论文指出「READY 缓冲允许高 CPU 开销的运行时准备在后台进行，而不阻塞 GPU 密集的智能体执行」。评估器的运行时预热在智能体运行期间进行；会话携带一个共享截止时间（deadline），超时的会话仍会进入后处理阶段，以恢复带有终止超时状态的部分轨迹。

### 轨迹重建（Trajectory reconstruction）

- **逐请求（per_request）**（保守基线）：每次补全（completion）生成一条轨迹——对单次调用无损，但会切碎连贯的会话；单个编码问题可能产生上百条轨迹。
- **前缀合并（prefix_merging）**：把补全切分为有序的链（chains）。仅当相邻补全满足严格 token 前缀关系 `p_{i_{m+1}}[1:|p_{i_m}|] = p_{i_m}` 时，它才加入同一条链。子智能体、并行分支、上下文压缩（context compaction）、prompt 重写会各自形成独立的链。一条链的 token 序列为 `p1 || a1 || u1 || a2 || u2 || ... || aK`，其中损失掩码（loss mask）在采样 token `a_m` 上取 1、在规范性插值 token `u_m` 上取 0；`a_m` 复制真实的对数概率，插值 token 使用合成条目。

正确性不变量：「训练中每个可训练的 token 都与 rollout 时的行为策略（behavior policy）一致，所有非生成 token 均被掩码掉。」

### GRPO 训练设置

- 基座模型（base）：Qwen/Qwen3.5-4B；数据：NovaSky-AI/SkyRL-v0-293-data 训练划分（293 个任务）；训练器：Slime 异步 GRPO；1 个 epoch；rollout batch size 为 4；每个 prompt 采样 16 条；前缀合并；优化器 Adam；学习率（LR）1×10⁻⁶；权重衰减（weight decay）0.1；启用 TIS。

## 实验结果

### SWE-Bench Verified（pass@1，同一 Qwen3.5-4B 基座）

| Harness | 基座（Base） | Polar RL | 提升 |
|---|---|---|---|
| Codex | 3.8% | 26.4% | +22.6 |
| Claude Code | 29.8% | 34.6% | +4.8 |
| Qwen Code | 34.6% | 35.2% | +0.6 |
| Pi | 34.2% | 40.4% | +6.2 |

### 训练奖励曲线（pass@1，前 10 步 vs 后 10 步）

- **Codex**：9.5% → 54.5%（从接近零起步，稳步上升）
- **Claude Code**：28.8% → 67.0%
- **Qwen Code**：61.6% → 66.0%（噪声较大）
- **Pi**：61.6% → 76.2%

最大提升（Codex，+22.6）被归因于模型适应了不熟悉的工具模式（tool schemas）/上下文策略；Qwen Code 的小幅提升（+0.6）符合预期，因为其基座已与该 harness 对齐。

### 轨迹构建器消融实验

在相同的 3 个训练步上：前缀合并把训练器数据流从 **1,185 次请求级更新削减为 218 次合并轨迹更新**；墙钟时间从 **189.5 分钟降到 35.2 分钟（5.39× 加速）**；rollout GPU 利用率从逐请求方式的 **20.4% 均值提升到 87.7% 均值**。逐请求重建配合结果奖励广播（outcome-reward broadcasting）会因噪声较大的信用分配（credit assignment）导致「显著的奖励黑客（reward hacking）」；会话归一化（session normalization）与 PRM 式信用分配已在路线图上。

### 离线 SFT 数据生成

用 Qwen3.5-122B-A10B（TP=8，max_model_len=32,768）驱动 pi-coding-agent v0.67.68，在来自 7 个仓库的 1,638 个 SWE-Gym 实例上运行；每个任务一个 Apptainer SIF；最大并发 max_concurrent=5–8；超时 3,600 秒。接受标准（Acceptance）= 最终补丁通过全部 FAIL_TO_PASS 与 PASS_TO_PASS 测试：

| 仓库 | 尝试次数 | 接受次数 | 接受率 |
|---|---|---|---|
| getmoto/moto | 343 | 184 | 53.6% |
| python/mypy | 257 | 101 | 39.3% |
| conan-io/conan | 71 | 27 | 38.0% |
| pydantic/pydantic | 81 | 24 | 29.6% |
| iterative/dvc | 219 | 45 | 20.5% |
| pandas-dev/pandas | 477 | 98 | 19.7% |
| dask/dask | 141 | 25 | 17.7% |
| **总计** | **1,638** | **504** | **30.8%** |

成本约 64 GPU 小时。每条轨迹平均 104 条消息、51 次助手回合（assistant turns），存在超过 200 回合的长尾。数据以 HuggingFace 数据集形式发布（Apache-2.0 许可），按仓库分层划分为 90/10 的训练/测试集。

## 结论与局限

**结论**：Polar「把智能体的测试时环境（test-time environment）当作 RL 系统的一等公民（first-class），而非需要移植进训练器的实现细节」。其核心设计选择是把集成边界移到模型端点：harness 正常运行，代理旁路观察 token 级流量，rollout 服务把已完成的执行转换为可训练的轨迹与奖励——从而让 rollout 可独立于训练与推理进行扩展，同时保留 harness 的非标准行为。

**局限**：
- 论文未设专门的局限（limitations）章节。最小的提升是 Qwen Code（+0.6 分），被描述为噪声较大。
- 逐请求重建配合结果奖励广播会产生奖励黑客（reward hacking）；目前尚未支持合适的会话归一化与 PRM 式（过程奖励模型式）信用分配，属「本文工作范围之外」。
- 框架对比（表 3）给竞品打了部分分数：Polar 声称在异步 RL、异步 rollout 分阶段、rollout-as-a-service、原生 harness 无关性等维度上提供一流支持，而 SkyRL-Agent、Agent Lightning、rLLM、OpenClaw-RL 等系统在这些维度上存在部分或缺失支持。
- 系统的服务 API（附录 A.5）包括 POST /rollout/task/submit、GET /rollout/task/{task_id}、GET /rollout/status、POST /callbacks/session_result，以及节点注册/心跳（heartbeat）端点。

## 与 harness × 模型训练的关系

「在任何 harness 上做 RL 训练」得以成立的关键，在于把 RL 的集成边界从 harness 内部移到模型 API 端点上：因为任何基于 LLM 的智能体都必然与模型通信，所以 LLM API 调用是存在于智能体自身之外的公共接口。Polar 把 harness 当作黑盒，通过代理（proxy）LLM API 调用、记录 token 级交互，并把完成的执行重建为对 token 忠实的轨迹，从而在不修改 harness 内部代码的前提下，让 Codex、Claude Code、Qwen Code、Pi 等任意现有 harness 直接充当 RL 环境。配合 rollout-as-a-service 的异步服务架构（每个 rollout 节点并行处理运行时预热、智能体执行、轨迹重建与评估，供独立训练器按规模消费），Polar 实现了与 harness、训练基础设施和 RL 算法三重无关的解耦设计；再结合 GRPO 等算法，即可对任意 harness 上的智能体进行大规模异步 RL 训练。
