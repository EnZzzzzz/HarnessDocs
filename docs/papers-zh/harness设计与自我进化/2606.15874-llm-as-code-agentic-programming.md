# LLM-as-Code：面向 Agent Harness 的智能体式编程（LLM-as-Code: Agentic Programming for Agent Harness）
- 作者 / 机构：Junjia Qi, Zichuan Fu, Jingtong Gao, Wenlin Zhang, Hanyu Yan（香港城市大学, City University of Hong Kong）；Xian Wu（腾讯杰维斯实验室, Tencent Jarvis Lab）；Xiangyu Zhao

- 原文链接：https://arxiv.org/abs/2606.15874
- 版本说明：v1 提交于 2026-06-14，v2 修订于 2026-06-22；被 KDD 2026 智能体软件工程研讨会（Workshop on Agentic Software Engineering, AgenticSE）接收

## 摘要（中文翻译）

主流的 LLM agent 框架让模型充当执行编排者，这是一个结构性错误。本文认为，"token 爆炸（token explosion）、控制流幻觉（control-flow hallucination）与不可靠完成（unreliable completion）并非实现层面的 bug，而是架构性后果（architectural consequences）——因为把循环（looping）、分支（branching）、排序（sequencing）这类确定性工作指派给了一个概率系统"。无论怎样的提示工程或模型规模扩展都无法根治这一问题。作为替代方案，本文提出"智能体式编程（Agentic Programming）"：所有控制流都由程序掌控，LLM 本身只是其中的一部分——作为一种自适应的组件，即"LLM-as-Code"，仅在需要推理或生成时被调用。在单次调用内部，模型拥有完全的自由度，但它无法改变程序的执行路径。由于控制权掌握在程序中，执行历史得以被组织为调用树构成的 DAG（有向无环图），因此"每次调用的上下文长度由它的调用深度决定，而非随步骤逐步累积"。针对计算机使用 agent（computer-use agent）的案例研究表明，这一设计能显著提升长视觉操作序列（long visual operation sequences）的稳定性。

## 核心贡献

- **架构层面的缺陷诊断（"范畴错误"）**：指出工作流同时包含两类步骤——确定性步骤（循环、分支、排序，编程语言已能以完美可靠性提供）与概率性步骤（理解、总结、判断，才是 LLM 的用武之地）。主流框架让 LLM 担任编排者，等价于"从概率分布中采样一条控制流边（sampling a control-flow edge from a probability distribution）"，token 爆炸、控制流幻觉与不可靠完成因此是架构性后果而非可被提示词或更大模型消除的实现 bug。
- **提出"智能体式编程"（Agentic Programming）范式**：程序主导全部控制流，LLM 作为"LLM-as-Code"自适应组件只负责推理与生成；模型在单次调用内灵活，但不可改变程序的执行路径。该范式包含四个组成部分：代码驱动的 agent 工作流、DAG 结构化的上下文、多 agent 协作、自编程进化（self-programmed evolution）。
- **"可靠性来自构造（reliability by construction）"**：规则由运行时强制而非请求模型遵循，合规不再被"采样"；失败被定位到"某个命名调用的返回值"，而非五十步转写（transcript）中的某一轮对话。
- **实证验证**：在 OSWorld 基准上，仅用 15 步即达 86.8% 的整体成功率，全面超越此前最强的 agent 框架、通用模型与任务专用模型（此前最优系统在 100 步上限下达 80.4%）。

## 方法（中文翻译）

核心论点：把确定性控制流交给概率模型是架构性错误。作者追溯编排者（orchestrator）设计源自 ReAct 的"推理-行动"循环，如今已衍生出 AutoGen、OpenHands、MetaGPT 等框架。其吸引力在于"一段提示词就能替代成页的编排代码"，但在长程（long-horizon）任务上会反复出现三种症状：

1. **token 爆炸**——上下文每步增长，直至截断摧毁早期信息（例如丢失一个根因假设）；
2. **控制流幻觉**——验证器尚未运行，agent 就声称问题已解决；
3. **不可靠完成**——因最新的失败测试而放弃此前正确的诊断。

现有的修复手段（更好的提示词、更长的上下文窗口、重试逻辑）都只是"收窄失败率而不消除它，因此在足够长的任务上失败仍会累积放大"。

**方法：程序拥有执行，LLM 负责推理。** 范式由四个部分组成：

**3.1 代码驱动的 agent 工作流（Code-driven agent workflow）。** 工作流用普通代码编写，运行时强制规则而非请求模型遵守——"合规不再被采样，因为规则根本不会被问及模型"。工作流并非固定流水线：一次 LLM 判断可以调用封装了自身 LLM 调用的普通代码，因此"调用图在运行时被展开，而非事先固定"。灵活性体现在递归深度，可靠性体现在每一层的代码。

**3.2 DAG 结构化的上下文（DAG-structured context）。** 一旦代码驱动执行，历史本身就构成调用图。作用域规则："一次调用能看到其完整祖先链的上下文"，已返回的子调用则坍缩为一行的摘要。示例：A→{B→C, D}——当 C 运行时任取其三层的完整祖先链；C 返回后，D 继承 A、B 的完整上下文以及 C 的摘要。上下文由此被限制在 O(深度) 而非 O(步数)。完整 DAG 保留在 harness 层面以供回放/调试，但"没有任何节点能看到它的全部"。

**3.3 多 agent 协作（Multi-agent collaboration）。** Agent 只是函数，并行即普通程序并行。并发 agent 是同一调用图中的兄弟分支；协调者"是图本身，而非一个监督模型"。两个实际后果：扩展规模受资源而非共享上下文窗口限制；agent 间接口是"类型化的返回值，而非自由形式的对话"——失败 agent 是一次失败调用，程序可以重试或放弃。文中以代码评审 agent 为例：为每个文件分发一个子 agent，在程序逻辑中汇总结果。

**3.4 自编程进化（Self-programmed evolution）。** 智能体函数可以在同一纪律下生成并改进其他智能体函数。提出替代方案是一次 LLM 调用，但结果"以代码的形式提交（只有通过调用方的测试才被接受）"。这恢复了普通工程实践：单元测试可以确定性地钉住 LLM 回复；失败被定位到"某个命名调用的返回值，而非五十步转写中的某一轮"。

## 实验结果

GUI 自动化 agent 在 **OSWorld** 上评测。

**表 1：整体成功率（baseline 上限 100 步，本方法 15 步）**

| 方法 | 最大步数 | 整体 |
|---|---|---|
| Holo3-35B-A3B | 100 | 80.4 |
| OpenAPA w/ Gemini-3.1-pro | 100 | 78.3 |
| Claude Sonnet 4.6 | 100 | 72.1 |
| **LLM-as-Code w/ Claude Sonnet 4.6** | **15** | **86.8** |

此前最强的系统止步于 80.4（正是本文预测的"采样控制器"的烧步数（step-burning）效应），而"我们的 agent 在代码中运行循环，以 15 步达到 86.8"。

**表 2：各领域细分（baseline 100 步，本方法 15 步）**

| 方法 | Chrome | Multi-Apps | OS | 整体 |
|---|---|---|---|---|
| Agent S3 w/ Opus 4.5 bBoN (N=1) | 61.7 | 57.4 | 75.0 | 66.0 |
| Agent S3 w/ GPT-5 bBoN (N=10) | 69.5 | 58.7 | 79.2 | 69.9 |
| Kimi K2.6 | 76.7 | 55.0 | 79.2 | 73.1 |
| OpenAPA w/ gemini-3.1-pro | 71.7 | 65.7 | 83.3 | 78.3 |
| Holo3-35B-A3B（专用） | 78.3 | 62.9 | 95.8 | 80.4 |
| **Ours（本方法）** | **93.5** | **80.0** | **100.0** | **86.8** |

本方法在三个领域及整体上均取得最优，领先于 agent 框架、通用模型和任务专用模型。作者将此归因于"可靠性来自构造"——必需步骤写进代码且"始终按既定顺序运行，因为没有采样决策能跳过、重复或错排它们"。第二个 agent（自主隔夜研究流水线）共享同一结构（每个顶层循环约 150 行 Python）。两个 agent 的这些性质"都继承自控制权所处的位置，而非任务专用设计"。

## 结论与局限

**结论。** 主流执行模型"犯了一个范畴错误"——把确定性工作指派给概率系统，因此这些失败是架构性的，"仅靠模型规模扩展无法解决"。本文的药方是："程序拥有执行，LLM 负责推理、生成与判断"，并以递归方式调用。收尾的问题是"关键不在于 LLM 能做什么，而在于谁应当控制执行"，答案是程序。

**局限（文中明确承认）。** 作者明确指出："智能体式编程并不涵盖所有 agent。"对于没有已知结构的完全探索性任务——例如开放式头脑风暴，或没有阶段模型的研究——"可能更适合 LLM 驱动的编排，这一点我们不持异议"。本文的主张刻意更窄：当一个工作流具有已知结构时，该结构应写成程序而非托付给模型。论文还指出其证据基础是两个生产环境 agent（GUI 自动化与隔夜研究流水线），均处理结构化任务。

## 与 harness × 模型训练的关系

对 harness 架构设计而言，这篇论文的核心启示是把"控制流归属"作为第一性问题：无论用何种模型、如何训练，只要 harness 把循环、分支、排序与任务完成的判定交给概率模型采样，token 爆炸与控制流幻觉就会在足够长的任务上复现——这是架构性后果而非训练数据或模型能力问题。据此，harness 应默认让程序持有控制流：将 agent 循环（读-想-做、验证-重试、多 agent 协调）编译为确定性代码，LLM 仅以函数/调用形式被嵌入，其输出被程序校验、转换与提交，而非作为"下一步做什么"的直接决策。上下文管理也应随之从"扁平日志、逐步骤累积"改为"调用树 DAG、按调用深度剪枝"，并保留完整 DAG 供回放与调试。模型训练层面的推论是：与其追求让模型"更可靠地自主执行长流程"，不如训练模型在受限调用内更好地推理、生成与返回类型化结果，同时把长流程可靠性的责任交给程序本身。
