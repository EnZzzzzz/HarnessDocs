## 摘要

Claude Code、OpenHands 一类编码 harness，会在基础模型外包上一层工具、记忆和规划机制；但在需要长时间行动、又只能看到部分环境的具身任务中，还没有同等成熟的方案。

我们首先汇报 Gemini Plays Pokémon（GPP）实验。通过**人在回路中（human-in-the-loop）**的方式——人类阅读 Agent 的运行轨迹，再手工改造 harness——GPP 成为第一个通关《宝可梦 蓝》《宝可梦 Yellow Legacy》困难模式以及《宝可梦 水晶》，并且没有输掉最终战斗的 AI 系统。在最困难的阶段，Agent 开始借助长上下文记忆自行调整策略，显现出自我改进的早期信号。

在此基础上，我们提出 Continual Harness：一个无需重置环境、可以持续自我改进的具身 Agent harness。它从最小环境接口出发，让 Agent 在行动与改造自身系统提示、子 Agent、技能和记忆之间交替进行，并能读取任意过去的轨迹数据。与必须完成一整个 episode、重置后才能优化提示的方法不同，Continual Harness 可以在同一段持续运行中在线适应。

在《宝可梦 红》和《宝可梦 绿宝石》上，Continual Harness 从零开始，在没有人工知识、手工工具和领域脚手架的情况下，显著减少了达到目标所需的按钮次数，并收回了与人工专家 harness 之间的大部分差距；收益大小取决于模型能力。

我们还让模型本身进入闭环：开源 Agent 的运行轨迹由前沿模型教师重新标注，再用来更新模型，从而形成在线的过程奖励协同学习。在《宝可梦 红》中，这套方法让开源模型在不重置环境的情况下持续推进游戏里程碑。

## 一、引言：怎样把人从改进回路里拿掉？

Agent harness 已经成为自主编码 Agent 的标准基础设施。它把基础模型和环境连接起来，让模型能浏览代码库、执行命令，并在长时间交互中保存状态。然而，具身 Agent 还缺少同等级别的 harness。

PokeAgent Challenge 表明，如果没有领域专用脚手架，前沿视觉语言模型在 RPG 游戏中几乎无法推进。GPP 项目说明，**人在回路中（human-in-the-loop）**的 harness 改进可以解决这个问题：团队先让 Agent 玩游戏，人类在回路里观察轨迹、发现卡点，再重写 harness；下一轮 Agent 带着修改后的工作系统继续行动。团队由此把最初的“截图 + 按钮”接口，逐步改成了多 Agent 系统。后期，他们又移除人写的专用 Agent，只留下 `define_agent`、`run_code`、记事本编辑和自定义工具创建等元工具，让模型在游戏中自行搭建子 Agent 和可复用脚本。

这些 Agent 在 2025 年 5 月通关《宝可梦 蓝》，同年 8 月击败 Yellow Legacy 困难模式的四天王，并在 11 月通关《宝可梦 水晶》。在 Yellow 和 Crystal 最难的阶段，模型开始通过长上下文记忆迭代自己的策略。

所以论文真正要问的问题是：**既然人类可以通过读轨迹、改 harness，让 Agent 一轮轮变强，能不能让 Agent 自己接替这个位置？** Continual Harness 的核心变化，就是用自动 Refiner 替换 human-in-the-loop 中负责改造 harness 的人。环境、Agent 和 harness 的关系不变，改变的只是“谁来读轨迹、谁来做修改”。

论文图 1 把演进过程分成三步：第一步是 human-in-the-loop，人类负责改 harness；第二步是 self-improving harness，自动 Refiner 在同一个连续 episode 内改 harness；第三步是 model + harness co-learning，除了 harness 状态，模型权重也加入更新。Continual Harness 因而不是凭空出现的新机制，而是把 GPP 中已经有效、但依赖人工的工作流程自动化。

系统从一个最小接口开始：画面、当前可见区域的 ASCII 地图，以及按钮输入。Agent 一边行动，一边利用本次 episode 已收集的轨迹，改写系统提示、子 Agent、技能库和记忆。每隔 $F$ 步，Refiner 读取近期轨迹中的失败信号，依次检查四类 harness 组件并执行增、删、查、改（CRUD）。整个过程不中断，也不重新开始游戏。

在三种 Gemini 3 模型——Pro、Flash、Flash-Lite——上，实验显示 Continual Harness 可以降低按钮成本，但增益依赖模型能力。随后，研究者把改进后的 harness 转给开源模型：先用过程奖励模型给轨迹打分，再让 Gemini-3.1-pro 重写低奖励片段，最后通过软监督微调（soft SFT）更新模型。这样，harness 改变模型将看到的轨迹，模型的新行为又暴露下一轮需要修复的问题。

本文贡献包括：GPP 首次让 AI 通关多款宝可梦 RPG；提出无需重置、能从最小接口在线搭建自身组件的 Continual Harness；证明它能收回与人工专家 harness 之间的大部分差距；并展示模型权重与 harness 状态可以在同一在线过程中持续协同学习。

## 二、预备知识：这里说的 Harness 到底包括什么？

### 2.1 具身 Agent 环境

在时间步 $t$，Agent 收到一帧画面 $o_t$，以及用 ASCII 描述可见地块和附近可行走位置的文字地图 $m_t$，然后从固定按钮集合 $\mathcal{A}$ 中选择动作 $a_t$。文字地图只包含人类能从屏幕上读到的信息，用来弥补当前视觉语言模型空间推理能力有限的问题；它不提供攻略、目标列表或寻路结果。

环境是部分可观察的：除了画面和地图展示的内容，Agent 看不到 NPC 意图、战斗机制等内部状态。

### 2.2 Agentic Harness

Agentic harness $\mathcal{H}$ 是基础模型 $M$ 与环境之间的脚手架层，由四部分组成：

- 系统提示 $p$：每一步提供给模型的指令和战略指导；
- 子 Agent $\mathcal{G}$：由主控 Agent 调用的专门模块，例如战斗策略、解谜和自我反思；
- 技能 $\mathcal{K}$：可复用流程，既包括推理时引用的规则，也包括寻路器、工具封装等程序；
- 记忆 $\mathcal{M}$：沿 Agent 轨迹持续积累事实、策略和观察的长期存储。

此外，harness 还提供 `define_agent`、`run_code`、`process_memory` 等固定元工具，Agent 可以用它们直接修改上述四部分。

极简 harness $\mathcal{H}_{\min}$ 只有环境接口、通用系统提示，没有子 Agent、记忆和人工技能。专家 harness $\mathcal{H}_{\mathrm{expert}}$ 则由人把四部分全部搭好。Continual Harness 从极简版本起步，加入自动 Refiner，根据轨迹不断原地改写四类组件；运行中的状态记为 $\mathcal{H}_{\mathrm{CH}}$。

## 三、方法：两个循环怎样接在一起？

### 3.1 同一个 episode 内改 Harness

令 $s_t=(o_t,m_t)$ 表示第 $t$ 步观察。内循环是正常行动：模型 $M$ 在当前 harness $\mathcal{H}_t$ 的包裹下，根据 $s_t$ 和已有轨迹生成动作 $a_t$。

外循环负责改造 harness。在预热 $W$ 步后，每隔 $F$ 步，Refiner 读取最近的轨迹窗口，找出失败信号，并生成

$$
\Delta=(\Delta p,\Delta\mathcal{G},\Delta\mathcal{K},\Delta\mathcal{M}).
$$

Agent 不重置。更新后的 $\mathcal{H}_{t+1}=\mathcal{H}_t\oplus\Delta$ 在下一步进入上下文。提示词直接替换，子 Agent、技能和记忆则接受 CRUD 操作。实验中 Agent 与 Refiner 使用同一个模型，只是调用时机和读取的轨迹上下文不同。

### 3.2 Refiner 每次具体改什么？

Refiner 从近期轨迹里寻找导航循环、工具调用失败、目标停滞和错过探索机会等信号，然后做四轮检查：

1. 根据失败与轨迹窗口重写系统提示；
2. 为反复出现的多步模式创建子 Agent，修复已有条目，删除长期没有有效使用的条目；
3. 把成功操作固化为技能，并修复抛出异常的可执行代码；
4. 补充缺失记忆、更新过时条目，并降低已经通过区域的记忆重要度。

早先发现的失败会继续留给之后的改进轮次。因此，信息会随 episode 变长而积累，而基于重置的方法每次更新后都要重新开始。更重要的是，很多失败只有在游戏后期才出现，例如后期战斗、多步谜题和长对话链；从初始状态反复重跑的方法天然更难触及它们。

### 3.3 模型与 Harness 的持续协同学习

预热完成后，每次在线迭代让策略 $\pi_{\theta_k}$ 在会实时改进的 harness 中运行 $K=256$ 步。成对过程奖励模型（PRM）给滑动窗口内的每个转移打 $[0,1]$ 分；低奖励窗口交给前沿教师重新标注，再在这些样本上做 soft SFT，得到 $\theta_{k+1}$。

第 $k$ 轮结束时保存的模拟器状态，会作为第 $k+1$ 轮的起点，因此游戏位置一直向前累积。模型动作决定轨迹 $\tau$，Refiner 根据 $\tau$ 修改 $\mathcal{H}_t$，新的 harness 又改变模型接下来会遇到的数据分布。模型权重在迭代之间更新，harness 在每次迭代内部更新，两者由同一批轨迹连接起来。

## 四、实验：它真的比人工搭建更好吗？

### 4.1 设置

实验使用《宝可梦 红》和《宝可梦 绿宝石》，主指标是**到达里程碑前累计按了多少次按钮**。一次工具调用即使批量发出三个按钮，也计作三次，因此不同工具封装仍可公平比较。

三种 harness 条件分别是：极简版本 $\mathcal{H}_{\min}$；带 A* 寻路、属性表、伤害计算器和人工目标的专家版本 $\mathcal{H}_{\mathrm{expert}}$；以及从极简版开始在线改进的 $\mathcal{H}_{\mathrm{CH}}$。后者又分为从零开始、载入已有成果后冻结、载入后继续更新三种。

所有条件都测试 Gemini 3 Pro、Flash、Flash-Lite；开源迁移使用 Gemma-4 的 E2B、E4B、26B MoE 和 31B dense。每项实验至少三个随机种子，正文报告种子中位数，并用淡色展示单次运行。

### 4.2 GPP 是怎样长出自己的工具的？

早期 Blue 版本依赖人写的寻路 Agent 和推石解谜 Agent。Yellow Legacy 之后，研究者把这些专用组件换成通用元工具，让模型自己搭 harness。模型曾主动把 `autopress_buttons` 的沙箱漏洞封装成通用 `press_sequence`，为 Crystal 最终战设计名为 “Operation Zombie Phoenix” 的多阶段策略，还在记事本里写出 Goldenrod 地下开关谜题的真值表。

Yellow Legacy 运行记录显示，技能和子 Agent 的 CRUD 修改贯穿全程，并没有收敛成固定脚手架；大多数修改集中在少量导航和战斗组件上。`battle_strategist_agent` 的提示经历扩张、简化和结构重写，最后把逐项判断吸收到一个负责分派多个子检查的 `master_battle_agent` 中。

### 4.3 与专家 Harness 的差距缩小了多少？

在两款游戏中，Continual Harness 到达每个受监控里程碑所需的按钮都明显少于极简基线，并收回了极简到专家之间的大部分效率差距。它没有读取游戏反编译结果、里程碑日程或专家版的手工子 Agent。

剩余差距主要出现在对话密集的道馆内部和多轮战斗策略上，系统还不能稳定合成这类组件。《宝可梦 红》中，载入旧 harness 后继续更新的版本在每个里程碑都比从零开始更高效，说明上一轮形成的 harness 即使换到重置后的新游戏，也能继续带来收益。

### 4.4 不是所有模型都能从自我改进中获益

在《绿宝石》的成本—完成度平面上，Pro 的 Continual Harness 严格帕累托优于极简基线：从零版本以约 130 美元中位成本达到 100% 里程碑，极简版花约 215 美元达到 98%，成本下降约 40%，完成度没有损失。两个 bootstrap 版本以 110–140 美元达到 96%–100%。

Flash 上的收益波动很大：载入后继续更新的版本以 42 美元达到 80%，略高于极简版以 30 美元达到的 77%；另外两种版本方差更高。

Flash-Lite 则出现反效果。极简版花 11 美元达到 20%，所有 Continual Harness 版本只达到 3%–13%，成本还相当或更高。结论很明确：只有模型足以正确利用这些组件，harness 改进才可能带来收益。

### 4.5 开源模型能否与 Harness 一起学习？

研究者先用前沿模型的 Continual Harness 轨迹做 SFT，再用逐步过程奖励做离线 GRPO。这两个预热阶段单独都没有带来有意义的里程碑推进。真正的进展从在线协同学习开始：每轮运行 256 步，PRM 打分，Gemini-3.1-pro 重标低奖励窗口，再做 soft SFT。

所有展示的运行都能跨训练迭代继续推进游戏，无论从游戏开头还是中期存档开始。作为负面对照，没有监督预热的 Qwen3.5 27B 和 35B 虽能生成格式正确的工具调用，却无法离开起始区域。这排除了“只是运行协议碰巧让游戏向前”的解释。

### 4.6 技能本身是否真的在变好？

研究者把导航技能的路径成本与 Dijkstra 最优解比较，使“技能变好”不再只靠最终游戏成绩间接推断。极简 harness 从不调用导航技能；每种 Continual Harness 条件都在 24 小时内累计调用数百次。

从零运行时，导航路径相对最优解的额外成本，一开始接近 50%，很快降到个位数并保持稳定。失败调用被 Refiner 诊断，同一个 episode 内技能就得到修复。继承技能并继续更新的版本始终不差于冻结版本，说明已有技能之上继续改进仍有价值。

## 五、相关工作

编码和助手任务中的 Agent harness 已经很常见，但具身 RPG 仍会因为缺少领域脚手架而停滞。已有提示优化和反思式自我改进方法通常在 episode 之间优化某个组件；Continual Harness 则在 episode 中途，根据局部轨迹原地修改完整状态 $(p,\mathcal{G},\mathcal{K},\mathcal{M})$。

游戏 Agent 有两条常见路线：要么在游玩过程中自建工具，要么让大模型配合人工规划器。GPP 证明人监督的 harness 迭代可以通关多款完整 RPG，本文则把这一过程自动化。

在训练方面，本文连接了无需重置的强化学习、上下文内强化学习、过程奖励、GRPO 和 STaR 式自训练。不同之处在于：它先用 SFT 与离线 GRPO 预热，再让前沿教师持续重标开源模型在实时改进 harness 中产生的低奖励片段。

## 六、讨论：能力下限和尚未回答的问题

Continual Harness 能从最小接口出发，在不重置的情况下搭建并修订自己的脚手架，在宝可梦任务中收回与人工专家 harness 之间的大部分差距。行动—改 harness 的交替同时发生在两个时间尺度：推理时，Agent 行动、Refiner 改组件；训练时，模型在同一个实时变化的 harness 中学习，数据分布也随自身策略共同变化。

但系统存在能力下限。Flash-Lite 在《绿宝石》上停在 20% 以下，所有 Continual Harness 版本都不如极简基线。协同学习实验也仍依赖前沿教师；受测开源模型最高到 Gemma-4 31B，还不足以同时扮演教师和学生。

实验也没有找到收敛点。论文只证明在已运行的训练时段内里程碑持续增加，没有证明最终会稳定到哪里。本文只研究把上一轮末尾状态接到下一轮开头的无重置训练；它也可改成传统的重置批训练，但二者在同一任务上的正面对照仍是开放问题。

# 附录

## 附录 A：宝可梦环境

实验涉及《宝可梦 红》（1996）、《宝可梦 水晶》（2000）和《宝可梦 绿宝石》（2004）。它们都是长时程单人回合制 RPG，包含地图导航、NPC 对话、回合制战斗、物品管理和由徽章、剧情节点组成的门控目标。

模拟器提供原生分辨率画面：Red/Crystal 为 $160\times144$，Emerald 为 $240\times160$，送入视觉语言模型前放大两倍。动作通道有八个按钮：上下左右、A、B、START、SELECT。每次观察让模拟器推进固定 120 帧，以便菜单、战斗文字和行走动画在两次决策之间完成。

ASCII 地图标出可行走地块 `.`、墙 `#`、可交互物 `?`、NPC `N`、台阶以及玩家位置和朝向，并覆盖屏幕外很小的一圈区域，让 Agent 能提前规划一步。它没有攻略、目标列表或全局地图。

Emerald 评测包含到第三个道馆为止的 31 个里程碑，Red 包含到第三个道馆为止的 18 个。主成本按按钮次数而非工具调用次数统计。

模拟器还可从 RAM 读取队伍、背包、HP、地图 ID、对话和战斗状态。专家 harness 的 A*、属性表和伤害计算器会用这些信息；极简版和 Continual Harness 只能通过文字地图和少量通用原语间接使用，不能访问预接好的领域工具。

## 附录 B：GPP 的补充证据

同一 harness 下，Gemini 3 Pro 在 Crystal 的早期阶段用约一半轮数、少约 60% token 达到与 Gemini 2.5 Pro 相近的里程碑。差异最大处在 Olivine Lighthouse：3 Pro 起初认为洞口危险，但排除更安全的假设后主动跳下并通过塔楼；2.5 Pro 困在错误假设循环里，在拿到 Fog Badge 前耗费 16,403 轮。

Yellow Legacy 四天王阶段的终身尝试次数为：Lorelei 18 次、Bruno 20 次、Agatha 18 次、Lance 19 次，Champion Pixel 第 4 次获胜。重试伴随越来越结构化的战斗提示和持久记忆，逐渐形成一套用文本编码的决策流程。

GPP 同样暴露了促使团队自动化的失败模式：不验证就接受假设；工具调用缺少参数；无法并行追踪多个目标。Goldenrod 谜题甚至持续数天，原因只是 Agent 跳过了战斗后 NPC 给出的关键提示。

Yellow Legacy 的 14 个战斗 Agent 检查点显示，结构从线性生存判断链，经历一次紧凑重建，再扩张成基于屏幕文字的程序，最后变为向五个具名子检查分发任务的主 Agent。Crystal Battle Tower 的 10 个检查点则逐步加入合法性、致命弱点、生存、换人规则、经验覆盖和显式速度计算。

### Power Plant 的 1,003 轮死循环

2025 年 8 月 29 日，Yellow Legacy Agent 在 Route 4 附近停滞约 3.5 小时，共 1,003 轮。它想前往 Power Plant，于是打开 Fly 菜单；多次选错后，它删除旧工具，创建带 `autopress_buttons: true` 的 `fly_menu_navigator`，并在长期记忆里要求自己信任这个新工具。

问题在于调用不符合 meta-harness 协议。要运行自动按键工具，JSON 的 `buttons_to_press` 必须显式写成 `["tool"]`；Agent 却根据逻辑填了 `["Down"]`。系统因此只在模拟器里按了一次向下键，根本没有调用工具。Agent 没发现这个差异，还在内部推理中认定工具已成功返回最优动作 `Down`，随后把同一 payload 重复了 842 次。

直到列表绕回起点 Lavender Town，它才意识到 Power Plant 不是第一世代可直接飞行到达的地点，退出菜单并步行前往 Route 10。这个案例揭示三点：新瓶颈出现后的前 50–200 轮最容易触发工具创建，停滞超过 500 轮后模型往往退回重复行为；持久记忆无法弥补调用协议错配；一旦误信工具已正常工作，Agent 会长时间忽视环境反馈。

## 附录 C：Harness 组件消融

### 寻路技能

研究者用所有运行在同一地图上见过的地块并集计算 BFS 最短路，再比较 Agent 在首次穿越两个里程碑之间发出的导航按钮。对话和战斗按钮被过滤。道馆内部由于对话和谜题状态更重要，顺序会反转，这也是与专家 harness 的剩余差距主要集中之处。

改进后的技能库大量生成 BFS 和 A* 封装，因为节省导航按钮会最快转化为新里程碑，是 Refiner 最容易看到的局部信号。极简到 Continual Harness 的大部分提升，仅技能库就能解释。

### 技能调试

对每个至少更新一次的持久技能，研究者比较更新前后的滚动调用成功率，也记录“创建—调用—重复调用—成功”的漏斗。结果是：大多数技能写完从未被调用，少数工作集吸收了绝大部分调用，真正成功的更少。

Refiner 因而采用近似分诊的行为：修复 Agent 真正在依赖的技能，容忍闲置技能退化，并接受一条很长的“创建后遗忘”尾部。无重置的价值在这里很直接：失败记录和修复动作位于同一条轨迹中。

### 子 Agent 交接

子 Agent 有两个作用：用狭窄的专用上下文降低每步成本，并让主控 Agent 在子任务结束后回到原目标。实验中子 Agent 的 token 曲线大约比主控低一个数量级。导航、对话和菜单任务的干净返回率，以及返回后继续原任务或十步内跨过里程碑的比例，都接近量表顶部。

### 记忆复用

每个主控步骤都会免费看到长期记忆条目的 ID 与标题目录；真正的问题是它会不会拉取正文、调用其中技能或在推理里引用条目。实验集中观察 Emerald 的 Mauville Gym 与 Red 的 Mt Moon。

从零运行会写很多记忆，却很少回读；预先继承成熟记忆库的 bootstrap 运行会在道馆和洞穴中主动查询。即便如此，绝对引用率仍然很低，大多数条目没有使用。论文据此认为，可迁移的单位是跨运行的完整 harness，而不是单次 episode，并提出未来应加入显式的复用偏好。

### Bootstrap 迁移与退化

Bootstrap 在新游戏开始前载入一次成功运行最终留下的技能、子 Agent 和记忆。Emerald 中，Agent 实际使用的各类存储都指向继承组件；Red 中技能和记忆仍以继承项为主，但 Agent 几乎放弃继承的子 Agent，改为少量调用新写条目，里程碑表现也同步退化。

Red 的退化约从第 213 步开始。新子 Agent 尚未经历旧组件那样的修复周期，单次调用成功率更低。可行改进包括：选择时偏向继承组件，或当新子 Agent 的任务已被旧组件覆盖且表现更差时自动删除。

## 附录 D：训练设置与结果

### 监督微调

Gemma-4 E2B、E4B、26B MoE、31B dense 使用 LoRA 微调，$r=256$、$\alpha=256$、bf16、8K 上下文，在 H200 GPU 上通过 Unsloth 训练。样本由截图、harness 提示和 Gemini-3.1-pro 教师响应组成。学习率 $2\times10^{-5}$，前 3% 线性预热，之后余弦衰减；每个模型在教师轨迹上训练一遍。

### 离线 GRPO

对教师访问过的每个状态，SFT 策略生成 $G=4$ 个候选。Gemini-3-flash-preview 按动作正确性（权重 0.6）和格式合规（0.4）独立打分，同一状态内做组归一化，再执行标准 GRPO。学习率 $1\times10^{-6}$，相对 SFT 参考的 KL 系数 $\beta=0.04$，每步 8 个状态，共 590 个优化步骤。

### 在线协同学习

每轮是 $K=256$ 步的 DAgger rollout，完整 harness 的提示、记忆、技能和子 Agent 都会继续变化。PRM 奖励由轨迹进展 0.4、动作正确性 0.3、推理质量 0.2、格式合规 0.1 组成。低奖励窗口由 Gemini-3.1-pro 重标，再对该分片做 soft SFT。

小模型虽然能把 SFT 训练损失降得很低，在真实 8K harness 提示上却会退化到 `tool_format=0`，说明信号强度与长上下文之间存在问题。31B SFT Emerald 模型在多数指标上也不如 26B 版本。

在线实验从游戏开头或固定中期里程碑启动，改变分片窗口、样本累积策略，并测试加入已完成目标的教师提示。所有运行都使用 256 步预算、3 个 epoch、学习率 $5\times10^{-6}$ 的 soft SFT，以及步幅 8 的成对 PRM。

推进并非平滑发生，而是在连续多轮奖励维持在约 0.40 或更高之后，以一段段突进的方式跨过里程碑，中间夹杂回退。恢复 checkpoint 后第一轮奖励会下降，通常两三轮内恢复；里程碑仍能在恢复后继续推进，因此作者把它视为恢复协议造成的奖励伪影，而不是游戏进展真的丢失。
