# WebGrader 论文解读：训练"会做网站"的模型，先得有个会判卷的考官

> 论文：WebGrader: Training LLMs for Web Development with Self-Evolving Programmatic Grader
> 作者：Boshui Chen、Huiping Liu、Shaolei Zhang（北京理工大学 / 北京交通大学 / 中国人民大学）
> 发布：2026-08-06，arXiv: 2608.06474
> 同目录文件：`webgrader-arxiv-2608.06474.pdf`（论文原文）、`paper-en.txt`（原文文本版）、`论文译文-zh.md`（全文译文）

## 一、问题是什么？

先说一个背景：用强化学习（RL）训练大模型，在数学和算法代码上已经走通了。为什么能走通？因为这类任务自带"标准答案"——数学题算出的数对不对，代码跑单测过没过，机器一秒钟就能判出来。奖励信号又准又便宜。这类"奖励能被机器直接核对"的 RL，论文里叫**可验证奖励强化学习（RLVR）**。

现在把同样的思路搬到网页开发上：让模型根据一句自然语言需求，生成一个完整的网站。问题来了——**一个网站"对不对"，不是看出来的，是用出来的。** 按钮点了有没有反应？表单提交后数据存没存上？页面刷新之后购物车还在不在？这些功能性的对错，只有真的在浏览器里操作一遍才能知道。

那现有的奖励办法是怎么判的呢？主要有两派，各自有一个死穴。

**第一派：手写测试脚本。** 针对每个任务，人工写一套浏览器自动化脚本，精确、可执行、可复查。缺点是写不起——每条新需求、每种新的网站结构，都得重新写一遍。RL 训练要喂成百上千条需求，靠人写脚本根本跟不上。

**第二派：让大模型当裁判。** 用一个视觉语言模型（VLM）或者 GUI 智能体去操作生成的网站，然后让它凭感觉打分。这一派能 scale，但它有个不太起眼、却很要命的毛病：**它可能还没走到"决定性的那一步"，就下了结论。**

论文附录里有一个特别典型的真实案例。需求是往表格里加一条记录。网站跑起来后，按钮点了，页面弹出了"记录添加成功"的提示——GUI 裁判多半就判过了。但实际上呢？表格行数从 4 还是 4，行数增量是 0，那条记录根本没进表格。**网站在"说谎"，而裁判信了。**

打个比方：这就像考试阅卷，第一派是出标准答案逐题对，准但出不起；第二派是让学生口述"我做出来了"，阅卷老师听个大概就给分。两派有一个共同的根因：**判卷这件事本身没有被当成一个需要被验收的工程对象。**

用论文的原话总结这对矛盾，就是：**脚本式奖励是可验证的但不自治，GUI 评分器是自治的但无法被独立验证。** 这里的"可验证"是指判卷结果能被人独立复查——脚本是确定性代码，跑出什么结果就是什么结果，日志摆在那里逐条可查；"自治"是指不需要人介入就能判卷——每来一条新需求，不用任何人写脚本，它自己就能上手。两派各占一头，WebGrader 想做的就是把这两头合到一起。

所以这篇论文真正想问的问题是：**能不能造一个既不用人写、又不凭感觉打分的"考官"？** 它自己看懂需求、自己出考题、自己上考场操作、自己收集证据，而且——它自己的判卷水平，先经过一场考试验收，合格了再上岗。

## 二、怎么解决的？

WebGrader 的回答可以拆成四层：先给考官建一个"考官培训班"，再设计一套"判卷流水线"，然后让考官在培训班里自我进化，最后把进化好的考官冻结起来去给 RL 发奖励。这也正是论文标题里"自我进化的程序化评分器"（Self-Evolving Programmatic Grader）的含义——"程序化"指判卷靠可执行的测试和执行证据，而不是模型凭感觉；"自我进化"指的就是那个考官培训班。

### 2.1 先解决一个前置问题：考官的水平怎么衡量？

要改进一个评分器（grader），首先得能量出它的好坏。但生成的网站千奇百怪，你怎么知道它判对了没有？

作者的办法很直接：**自己造一个带答案的考场。** 他们从公开的 WebGen-Instruct 训练集里挑了 100 条需求，每条配一个在本地验证过能跑起来的 React/Vite 应用——这是"干净版"。然后往每个干净应用的源码里注入 8 个天然会出现的单点故障（改业务逻辑，而不是埋标记），比如校验失效、状态不持久、跨页面不同步。最终得到 100 个干净应用和 778 个活跃故障变体，按页面切成 60/20/20 的训练/验证/测试集，互不污染。

这个环境叫 WebGen-Verifier-100。有了它，评分器的每一次判卷都有标准答案可对：该抓的故障抓到没有（召回率），干净页面有没有被冤枉（特异性）。**说白了，就是先给考官出一套有标准答案的模拟卷。** 这个思路本身就是论文的一个核心主张：评分器在上岗发奖励之前，应该先对照可验证的结果被评估和改进。

### 2.2 判卷流水线：先出题，再看卷；先取证，再判决

接下来是 WebGrader 怎么判一个网站。这里有两个关键设计。

**第一个设计：需求先行（requirement-first）。** 给定一条需求，WebGrader 第一步**不看生成的代码**，先从需求文本本身推导出"这个网站应该具备哪些交互流程"。比如需求说"用户可以收藏职位并在刷新后保留"，那就推出一条流程：登录 → 收藏 → 刷新 → 检查收藏还在。

为什么要先看需求、后看代码？因为顺序反了就会出问题：如果先看代码里有什么再出题，代码里缺的功能就永远不会被考到——缺考而不是零分，这是两回事。WebGrader 规定：**从需求推导出来的流程，一条都不许删。** 功能缺失？那就按零分记（Fail），而不是当它不存在。

每条流程被写成一个**流程契约（Flow Contract）**，包含七样东西：前置条件、测试数据、动作序列、目标动作、证据检查点、后置条件、权重。可以理解成一张标准化的考卷题面：不仅要写"考什么操作"，还要写"操作前要达到什么状态、操作中要留什么证据、操作后怎么算对"。

**第二个设计：四段分离的流水线。** 拿到契约后，判卷分四步走：

1. **规划（plan）**：从需求出契约；
2. **落地（ground）**：对照生成项目的源码和实时 DOM，把契约编译成 Playwright 脚本——比如"点击保存按钮"要落实成页面上真实存在的一个选择器；
3. **取证（execute）**：在真实的 Chromium 浏览器里执行脚本，沿途收集四类证据——截图、DOM 快照、网络响应、持久化存储状态；
4. **判决（judge）**：一个 LLM 评判拿着证据和契约的后置条件比对，给出 Pass / Fail / Inconclusive。

注意这个分工的用意：**判决被安排在取证之后，而且只能基于证据判决。** 前面那个"假成功"的案例，在 WebGrader 这里就过不了关——成功提示只是弱证据，表格行数才是决定性证据，后者没变化，判 Fail。后文进化出来的技能库里，有一个技能就是专门治这种病的，叫**决定性证据裁决（Decisive-Evidence Adjudication）**：弱的视觉线索不能压过显式的状态证据。还有一种情况叫 Inconclusive：不是网站的锅、而是裁判自己这边出了问题（选择器歧义、浏览器超时等），这时不下结论，以免冤枉好人。

### 2.3 考官怎么进化：哪里错了修哪里，修完还要考试

初版考官（V0）肯定有不少盲区。怎么办？WebGrader 用了一个**残差驱动（residual-driven）的循环**，说白了就三步：考试 → 分析错题 → 针对性补课。

具体地，让当前考官在 WebGen-Verifier-100 的训练切分上跑，把所有判错的案例收集起来。一个由 Claude Opus 4.8 扮演的"错题分析师"（离线元评估器）把错误聚类，并且——这是关键——**归因**：每道错题归到流水线的四个环节之一：是契约出得不全（规划）？选择器没找到（落地）？证据没采够（取证）？还是证据够了却判错了（判决）？

归因之后，只针对出问题的那个环节做一个小而具体的修补，这种修补叫**技能（skill）**。比如："可执行 fixture"技能负责在测试前把缺失的前置状态造出来；"步骤对齐证据"技能负责把每条观察绑定到产生它的那一步，防止张冠李戴。这个"小步变异 + 选择"的套路，作者说是受了神经架构搜索（NAS）的启发——模型权重一个都不动，改的只是验证器的行为产物。

补完课不能直接上岗。每个候选技能要先在训练用例上自查，再放到**互不重叠的验证集**上考试：只有整体指标变好、且原来判对的案例一个都没判错（无回退），才被"晋升"。晋升的技能挂进一张**技能图（SkillGraph）**，图里记着谁依赖谁、谁能和谁组合、谁和谁冲突。实际判卷时，一个路由器按当前需求只激活相关的少数技能——平均每例只激活 1.46 个。

这里有个对照实验特别能说明问题：如果把所有发现的规则不分青红皂白地平铺进提示词（flat rules），token 用量涨了 29%，判卷 F1 却几乎不动（0.7813 → 0.7896）；而路由式技能图在相近的 token 预算下把 F1 拉到 0.9037，加冲突处理再到 0.9248。**换句话说，有效的不是"记住更多规矩"，而是"在对的时机用对的规矩"。**

整个进化分三轮，依次补规划/落地、落地/取证、判决的短板。故障召回率一轮一轮爬坡：0.650 → 0.744 → 0.800 → 0.850，冤枉干净页面的比率同时从 20% 降到 5%。

### 2.4 冻结，然后发奖励

进化完成的考官被**整体冻结**——流程、技能图、路由器都不再变。这一步很重要：RL 训练期间奖励函数必须稳定，否则策略追到的是一个移动靶。

冻结后的 WebGrader 给每个 rollout 算分：确定性流程（Pass 或 Fail）按权重算一个功能得分 I，再和外观分按 70/30 混合（R = 0.7×5I + 0.3×A），送进标准的 GRPO 算法训练策略模型。底座是 Qwen3-8B，先 SFT 再 RL，100 个有效更新步。

## 三、效果怎么样？

### 3.1 先说公平性

这类"我的奖励更好"的论文，最怕的是比较不公平。作者在这件事上做得比较扎实：所有受控变体共享同一个初始化检查点、同一批 600 条训练查询、同样的采样和优化配置，**唯一的变量是奖励怎么构造**。评估时所有模型（包括外部的大模型）都在同一套冻结的评估流水线下从头重测，连评估器的版本、提示词、内容哈希都固定留档。而且用了两套互相独立的评估器：WebGen-Bench 靠 UI 智能体操作打分，WG-core-250 靠确定性浏览器测试——防止"考官给自己出的卷子提分"。

### 3.2 主要数字

在 WebGen-Bench 上，8B 的 WebGrader-RL 功能成功率（FSR）达到 **52.01%**，比"外观分 + 未进化脚本"的对照组（44.13%）高 **7.88 个点**，而外观分几乎没变（只差 0.02）——说明涨的确实是功能，不是颜值。放到外部模型里看，它超过了 o4-mini（40.65）和 DeepSeek-v4-flash（47.91），跟 480B 的 Qwen3-Coder（53.25）基本持平；但离最强闭源模型还有明显距离——Claude Opus 4.8 是 68.20，GPT-5.5 是 62.44。这一点作者没有回避：**一个 8B 模型靠更好的奖励能打到第二梯队头部，但奖励再好也补不平基座能力的差距。**

在独立评估器 WG-core-250 上，它比对照组高 6.58 分（Full Score）和 6.41 个测试通过率点，统计检验也过硬：McNemar 检验 p = 7.3×10⁻⁵，bootstrap 置信区间不含零。收益分布在全部六个网站类别上（+4.73 到 +15.20 不等），不是个别任务撑起来的。

### 3.3 有意思的发现在"分数涨在哪儿"

考官进化后，提升最大的不是最后的"判决"环节，而是判决**之前**的执行环节：强证据收集 +15.6 个点、必须观察项覆盖 +14.9、动作后状态到达 +14.4、目标动作执行 +13.6。这印证了论文的核心论点：**大多数误判不是法官不行，而是根本没走到现场。** 先到达决定性状态、看到后果，判决自然就准了。

而且场景越难，进化赚得越多：多动作有状态的故障召回率涨了 24.3 个点，中高严重度的涨 28.1 个点，深度 2–3 层的流程涨 25.0 个点。

坏消息也要说。残留的错误集中在两类地方：**深度 4 层以上的长流程**（召回率只有 0.789）和**数据绑定、搜索/筛选/排序**（0.789–0.810）。长轨迹和弥散的数据依赖，仍然是这套取证式方法啃不动的硬骨头。另外留一法（leave-one-skill-out）消融显示，六个被测技能虽都净贡献为正，但单个技能禁用时也会误伤 1–2 个原本判对的案例——技能之间的组合并非完全无副作用。

## 四、写在最后

这篇论文表面上是"网页开发 RL 的一个新奖励"，但它真正立住的是一个更普遍的做事方式：**当任务的成败只能通过交互显现时，奖励本身也需要一个 harness。**

对做 Agent 工程的人来说，启发很直接。我们习以为常地把"评分器""裁判模型"当成训练流水线里一个静态的零件——写好 prompt，上线，然后祈祷它判得准。WebGrader 给出的答案是：裁判也要先建考场、先摸底考试、再针对性补课、最后持证上岗。判卷能力从 65% 的故障召回率进化到 85%，下游策略的功能成功率就实打实地涨了近 8 个点——**考官的质量，就是学生成绩的上限。**

另一个值得记住的细节是"需求先行"这个看似简单的顺序。先出题再看卷，缺失的功能才有零分；先看卷再出题，缺失的功能就永远缺考。这个原则放到任何"用模型评估模型"的场景都成立：**评估集应该从需求推导，而不是从被评估者的输出推导。**

至于局限，论文自己也交代得清楚：深度 4+ 的长交互流程、数据绑定类功能仍是盲区；进化过程依赖一个由更强模型（Claude Opus 4.8）扮演的错题分析师，这套"强带弱"的成本和闭环能不能进一步自治，是留给后续工作的口子。
